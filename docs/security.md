# Security and privacy design

secondHand has no application backend. The desktop process is the sole owner of saved applicant information. It serves no HTTP endpoint. The shipped UI and extension contain no analytics, cloud AI, remote fonts, or app updater. Dependencies and build artifacts are downloaded during development/build; this is separate from applicant data processing. The only things the desktop app itself downloads are the Laya model and the file that names its newest version, and only while Laya is on. Laya is on unless the person turns it off (see [Local AI with Laya](#local-ai-with-laya)).

## Vault

`vault.secondhand` contains AES-256-GCM ciphertext with a random 96-bit nonce for every write, a 128-bit authentication tag, and version-bound authenticated additional data. Version 2 files encrypt contents with a random 256-bit data key. That key is stored only in wrapped form, in separate AES-256-GCM key slots:

- **password**: wrapped by a key derived from the user's password with a random 256-bit salt and scrypt (`N=32768`, `r=8`, `p=1`). The password must be at least 12 characters.
- **recovery**: wrapped by the same scrypt derivation of a one-time recovery key (160 random bits shown as 32 Crockford base32 characters). It is displayed once, never stored by secondHand, and replacing it removes the old slot.
- **device** (optional): wrapped by an HKDF-SHA256 key from a random 256-bit secret. The secret is sealed with Electron `safeStorage` (macOS Keychain or Windows DPAPI) in `device-reset.bin` beside the vault, so it only works for the same operating-system account. Anyone who can use that signed-in account can therefore reset the password; users who share an account should turn it off in Privacy & backups.

Resetting a password unwraps the data key through the recovery or device slot, authenticates and validates the contents, and writes a new password slot; the encrypted contents are unchanged. Version 1 files (contents keyed directly from the password) still open. Adding a recovery key or device reset upgrades them to version 2 and reuses the existing password-derived key as the password slot, so the password does not change. KDF parameters are fixed and validated when reading a backup, preventing a file from requesting arbitrary computation.

The password, recovery key, and keys are never written to settings. A copied recovery key is cleared from the clipboard after one minute if it is still there. The unlocked key is held in the desktop process and its buffer is cleared on lock. JavaScript strings and copies cannot be reliably zeroed; an unlocked machine and its memory are outside the confidentiality guarantee. The UI clears profile/application state when notified of a lock. The app locks after ten minutes without relevant activity, on system suspend, on supported OS lock-screen events, and on exit.

Writes serialize through a queue, use a private temporary file, sync that file, and atomically rename it. Unix data files are mode `0600`; Windows uses the current user's application-data directory and inherited access controls. Whole-vault size and field lengths are bounded. There is no unencrypted SQLite sidecar, journal, or document cache. Local document reading can propose text fields for review, but does not store source documents or raw OCR in the vault. Only selected details explicitly saved through the profile workflow are persisted.

Profile choices for address availability, mailing address, applicant status, programs, and medical-bill help use explicit `yes` / `no` / unanswered values. Unanswered never becomes No, and program selections do not imply eligibility. Home and mailing details remain separate. Existing encrypted profiles load with new fields unanswered, without a format migration or automatic rewrite. The fictional full-applicant test fixture is not a product default and must never be submitted to the live portal.

Encrypted export is available through the operating system's file dialog. Import requires a locked vault and explicit confirmation before replacing existing records. The prior encrypted vault is retained as a rollback file. An imported envelope is structurally validated before writing; authentication and payload validation happen when the user supplies its password or recovery key. Keep an independent backup. Losing both the password and the recovery key (with no device reset available) is not recoverable by secondHand. A backup keeps the key slots it was saved with, so an old recovery key still opens a backup made before the key was replaced.

## Desktop isolation

Only packaged local HTML/CSS/JavaScript is rendered. The window has Node integration disabled, context isolation and sandboxing enabled, spellcheck disabled, restrictive Content Security Policy, denied permissions, blocked network requests, and denied navigation/new-window requests. A narrow preload exposes named actions; the main process verifies the IPC sender, top-level frame, and exact renderer URL. The portal-opening action uses a fixed official URL.

## Local document reading

The unlocked desktop can read a user-selected PDF, PNG, or JPEG through its native file picker. It does not move, modify, or retain a copy of the original. The source-size limit is 30 MiB and the PDF limit is 12 pages. The worker bounds rendered OCR pages to 16 megapixels, rejects PNG/JPEG headers exceeding 40 megapixels, rejects image dimensions over 20,000 pixels, bounds extracted text and word output, and limits engine processing to five minutes. Per-page limits are 200,000 text characters and 12,000 words per pass; combined document limits are 500,000 text characters and 80,000 words across both passes. Native file-picker and file-opening time are separate from the engine timeout.

PDF.js, Tesseract.js, its WebAssembly runtime, and the English language model are bundled for local processing. OCR needs no runtime network request, separately installed executable, API key, or Laya inference. Processing takes place in a hidden sandboxed Electron window with Node integration disabled, context isolation, and a dedicated temporary browser session. The session permits the fixed bundled assets and blocks network requests and other resources; navigation and new windows are not document operations.

The main process releases the source buffer, clearing bytes where possible, and destroys the worker window at completion, cancellation, or lock. The app clears temporary review text and candidates on discard, when leaving Documents, or on lock. Cancellation revokes pending results even if an operating-system picker cannot be dismissed programmatically and returns a late choice. No document database, original-file copy, or persistent OCR cache is created. As with other decrypted UI data, clearing JavaScript references cannot guarantee physical erasure of strings or operating-system memory.

Structured 1040/1040-SR candidates are layout-based suggestions requiring user review. The runtime retains automatic- and sparse-segmentation results from the same image; the parser omits SSNs and tax amounts unless both passes agree. These are correlated readings by the same model, so agreement and high OCR confidence do not establish correctness. Multiple detected tax-return headers produce no profile suggestions. Selected primary-applicant details populate an unsaved profile draft; only an explicit profile Save encrypts and persists them. Historical tax year and annual amounts, spouse/dependent details, filing status, and age/blindness marks do not become current income, household members, birth dates, or eligibility answers automatically. Generic documents expose extracted text for review without assuming a tax-form layout. Reading a document neither changes the saved profile nor releases anything to the browser extension or a destination site.

The original file's own permissions, cloud sync, backups, and retention remain unchanged. OCR errors and incomplete layout support can produce incorrect or missing suggestions, so recognition is not identity verification or validation of a benefits answer. [Document OCR](document-ocr.md) describes the review flow, limits, and synthetic test scope.

## Extension and local bridge

The extension uses Manifest V3, `activeTab`, `scripting`, `nativeMessaging`, and `sidePanel`. It requires Chrome 116 or newer. Its default host permission is limited to `https://hhsservices.iowa.gov/*`, and its static content script starts only on the Iowa portal path. Optional HTTPS host permissions let the user enable other sites individually, or every HTTPS site at once (see [SecondHand on all websites](#secondhand-on-all-websites)). Those sites require both Chrome's origin permission and a separate desktop trust prompt before field release; embedded forms require their own origin approval unless all websites is on. Dynamic content-script registrations and Chrome permissions can persist, but the extension has no storage permission or applicant-data persistence.

The page-hosted widget is an extension-origin iframe inside a closed shadow root, so the page cannot script it. The worker binds its requests to the iframe's own tab and accepts Autofill only from a trusted click with `confirmed: true`. The checklist lives in Chrome’s native sidebar. The worker accepts applicant operations only from the supported extension surfaces; content scripts and page `postMessage` calls have no direct path to the vault. Displaying either surface does not start filling. Iowa requests validate the exact HTTPS origin and portal path; other sites use their approved HTTPS origins.

The widget and sidebar receive field metadata, completion/missing/manual status, counts, and messages, never saved profile values or input values entered on the page. Clicking a checklist item or a **need you** link asks the content script to focus the corresponding control; it does not retrieve a saved answer. Generic mapping may send unmatched field labels, types, and choice text to Chrome's on-device AI in the extension page. It receives only allowed profile-key names, never saved answers, and has no cloud fallback. The mapper uses an already available local model rather than starting a model download. Plans and autofill results live in worker memory and clear when the tab navigates or closes; no applicant record is written to extension storage or an application backend.

The sidebar's "What this page says" section sends a page's visible text to Chrome's on-device Summarizer in the extension page. The text leaves out form controls, their choices, SecondHand's widget, and hidden content, so it never holds a typed or saved answer. On Iowa, only the information-only screens are read. Other sites are read only after they are turned on. The Summarizer model downloads only after the applicant clicks. Page text and key points live in worker memory for the tab. Iowa screens are kept until the tab leaves Iowa or closes. There is no cloud fallback.

Chrome Native Messaging invokes a local host registered with an exact extension ID. The native host relays bounded, framed JSON over a Unix socket or Windows named pipe to the running desktop. A fresh random session token authenticates local requests; its file is readable only by the current Unix user and protected by the user's directory permissions on Windows. Requests are strictly typed and reject unknown fields. A request cannot run shell commands, access arbitrary files, or fetch arbitrary profile paths. On macOS and Linux, an `openApp` request with the app closed makes the host start SecondHand itself: its own executable (in development, with the app path), with no shell, no Chrome origin, and nothing from the request, at most once per host process. On Windows, the relay starts only the `secondHand.exe` installed in its own folder, by its full path, with no arguments, no shell, and no inherited handles (Chrome's native-messaging pipes stay with the relay), and with the relay's environment less the test-only settings, at most once per relay process.

The desktop's explicit Prepare Chrome extension action copies a fixed allowlist of bundled assets into its local `chrome-extension` folder and registers the ID derived from the manifest's public key. No vault data is copied, and no Chrome settings or enterprise policy are modified. Chrome's Developer mode / Load unpacked step remains manual. The public manifest key provides a stable development ID, not cryptographic proof of the code of an unpacked extension. Folder/clipboard IPC methods accept no arbitrary paths or clipboard payloads. A missing extension bundle does not prevent using the local vault.

On Windows, a small compiled C# host relays bounded binary messages directly to the desktop's authenticated local named pipe. It does not launch Electron, open the vault, or store applicant fields. Its source is included and it uses the installed .NET Framework. This avoids Electron's Windows stdin/console behavior interfering with Chrome's length-prefixed protocol. macOS/Linux use the executable's native mode with raw descriptor streams. No global environment setting, localhost server, external runtime download, or shell command is needed by the Windows host at application runtime.

This bridge does not protect against malicious software already running as the same OS user. Such software could read process memory, the bridge token, or impersonate a local client. The native host's origin argument is an application integration check, not proof against a hostile local process.

Field release is controlled by one desktop setting, **Let Chrome autofill without asking** (`autofillWithoutAsking`). It is off by default.

- **Off:** each field-release request shows a desktop dialog naming the destination and requested fields. A multi-page Iowa run can make several requests. The buttons are **Cancel**, **Allow once**, and **Always allow on this computer**; sensitive requests on other sites offer only Cancel or Allow once.
- **On:** the setting is saved in `settings.json` next to the registered extension ID and separately approved site origins, never in the vault. The desktop returns eligible requested values without a dialog only while the vault is unlocked and only to that same authenticated extension ID. Iowa requests must use the allowlisted portal destination. Other HTTPS origins must be in the desktop's trusted-site list, or all websites must be on. All requested field names are allowlisted.
- **Other-site sensitive fields:** SSN, date of birth, earned/other income, assets, and medical expenses require confirmation for every request even when the setting is on. The worker excludes its designated sensitive keys from optional AI guesses.
- **Resetting it:** registering a different extension ID turns it off. Locking the vault (manually, after 10 idle minutes, on suspend, on supported OS screen-lock events, or on exit) stops all releases until the user unlocks again.

Dialogs recheck the unlocked vault, the access revision, and the extension connection before releasing fields, so a lock and re-unlock while a dialog is open invalidates it. Only requested, nonblank values are returned. Native `status` and `getFields` responses include an `accessRevision`: a randomly seeded, process-local safe integer that changes with lock, profile, trust, or registration changes. Before a fill or verified applicant/address continuation, the worker checks a fresh unlocked status against its authorization receipt and rechecks the tab/document. A desktop restart invalidates earlier receipts. This is separate from the renderer's `lockRevision`, which deduplicates lock responses and notifications without discarding a newer lock.

An empty `getFields` request is allowed only at the exact observed Iowa `enterPersonalInfo` and `addressValidation` endpoints, without query, fragment, or trailing slash. It runs the same unlocked/trust/consent gate, then returns empty values and an access receipt without reading the saved profile. This supports a fresh authorization for the disclosed navigation actions below, including an address page that needs no saved fields. Values from nonempty requests stay transient in the worker/content script for that fill operation and are never written to extension storage.

The trade-off is deliberate. With the setting on, anyone who can use the unlocked computer's Chrome can fill eligible saved answers into Iowa or separately approved sites (every HTTPS site while all websites is on) without a prompt, and can start the disclosed Iowa continuation actions. The vault lock and the 10-minute idle lock are the boundary. The desktop cannot independently attest a Chrome tab ID or document identity: it validates the authenticated extension, the destination string, and the field names. Binding a fill to its tab is enforced by the shipped extension code, not guaranteed against hostile software controlling that extension or the same OS user. A fresh status check also cannot make a subsequent browser mutation atomic with a desktop lock.

The Iowa adapter checks known page context and exact field labels, skips hidden/ambiguous/pre-filled inputs, and rechecks element identity before filling. User-started Iowa autopilot can continue recognized information screens. It can also choose ordinary Save and Continue on the verified, complete initial applicant page and select the first verified home-address suggestion before Save and Continue on the observed address-confirmation page. The desktop approval and persistent-trust copy disclose that these actions send answers to Iowa and require the user to review the chosen address before final submission. Single-use snapshots bind the address controls, text, selection, hidden form state, URL, and document; mailing suggestions, visible county questions, errors, and visible dialogs pause automation. Address selection is a preference among Iowa's candidates, not a determination that an address is correct.

### SecondHand on all websites

One switch in the side panel, **Use SecondHand on all websites**, turns SecondHand on for every HTTPS site. It needs two approvals, in order: the click asks Chrome for `https://*/*` (already an optional host permission in the manifest) before anything else is awaited, and the worker then sends `trustAllSites`, which shows one desktop dialog and saves `allSites: true` in `settings.json`. If either is declined, Chrome's access is removed again and nothing is registered. On approval the worker registers one content script, `site-all`, for every HTTPS page except Iowa's site, which keeps its own scripts.

What it allows: the site engine and its card run on every HTTPS page and in their frames, and the desktop accepts `getFields`, `suggestFields`, and `answerFields` from any HTTPS origin as it does from a trusted one. The card shows only on a page with a question the rules match to a saved answer or Laya could take; search boxes, the user name or email beside a password, and verification codes don't count. A frame's content script tells the worker only yes or no; the worker passes that to the page's top frame and nothing reaches the desktop.

What it doesn't change: nothing is filled until the applicant clicks Autofill; on sites other than Iowa's the extension never clicks Next or Submit; sensitive fields (`SENSITIVE_FIELDS`) still need the named confirmation on each site, even with **Always allow on this computer**; passwords, verification codes, signatures, and unknown household members are never filled; locking the app stops autofill; Laya's sensitive-facts prompt stays; no form text or saved answer leaves the computer.

Turning it off: **Turn off on all websites** in the side panel unregisters `site-all`, removes `https://*/*`, takes the card off open pages that are no longer on, and sends `untrustAllSites`, which needs no unlock. **Turn off** on the app's Chrome extension page clears `allSites` at once; the app reports it in `status`, and the extension turns itself off at its next desktop request. Until then the app refuses origins that aren't in `trustedSites`. Per-site registrations are kept. Chrome, when it removes `https://*/*`, also takes back every origin that pattern covers: sites turned on one at a time, and SecondHand's own access to Iowa's portal until Chrome restarts. The worker checks each one afterwards and the side panel names them.

The optional DOB repeat fill on the verified primary-applicant Tell Us More page always leaves Next manual. Other question pages and generic sites do not auto-advance. Generic rules can fill supported fields on permitted pages but must not bypass recognized Iowa manual/protected steps. The extension never signs or submits an application, accepts consent, solves CAPTCHA, or fills credentials. It does not invent unanswered household, legal, or eligibility choices. Current portal coverage and evidence are in [iowa-portal.md](iowa-portal.md).

Explicit choices may reveal additional verified applicant fields. Each applicant fill operation requests its mapped profile fields once and fills them in at most four fresh-preview passes. A run attempts each key at most once on that page. Saved answers that are blank are reported as fields that need the user, never retried in a loop. User-started Iowa autopilot stays in worker memory, stops on cancellation/failure or after its step limit, and does not confer authority to sign or submit. Other-site autofill requires a separate explicit click and never navigates.

## Local AI with Laya

Laya is a decision model that helps recognize form questions. It is on by default. The Chrome extension view has one toggle, **Find more fields with Laya (runs on this computer)**, with the model's status (off, not downloaded, downloading with progress, ready, error, or no model available yet), its size, and what the last update check said, plus download, pause, and remove controls.

- **What is downloaded:** the fine-tuned Laya checkpoint exported to int8 ONNX: `model.onnx` (3.8 MB), `model.onnx.data` (421.3 MB), the tokenizer (3.6 MB), and its calibration settings, 428.7 MB (429 MB) in all for the current export. It is never bundled with the installer.
- **When:** while Laya is on, the app downloads the model in the background as soon as it starts, if the model isn't on the computer yet. This needs no unlock, because it reads and sends no saved information. A new install, or one where the person never chose, counts as on. Turning Laya off is saved and stays off: nothing is checked, downloaded, or loaded while it is off. Pause keeps the partial file; the download resumes with an HTTP range request when the person clicks Resume, or at the next start. Remove deletes the model and turns Laya off, so it isn't downloaded again until Laya is turned back on. After the download, decisions work fully offline.
- **Pinning:** `desktop/laya-model.json` pins the model the app ships with: a Hugging Face commit, a prompt format, and for every file its URL, size, and SHA-256. It is the model downloaded when nothing is installed and the update check can't be read. Downloads use https; a redirect is followed only to another https address.
- **Updates:** at startup and then every 24 hours while the app runs, and only while Laya is on, the app reads `latest.json` from the `main` branch of [huggingface.co/JacobTDang/secondhand-laya](https://huggingface.co/JacobTDang/secondhand-laya). It has the same form as `desktop/laya-model.json`: a revision, a `format`, and every file's URL (pinned to the commit that holds it), size, and SHA-256. When its revision differs from the installed one and its format is one this app can run, the new model downloads in the background into its own `models/laya/<revision>/` folder while the installed model keeps answering. Only once every file matches its size and SHA-256 does the app switch to it: a decision already running finishes on the old model, the next one loads the new model, and then the old revision is deleted. An update never starts while the model is downloading, and the switch waits for running decisions. With nothing installed yet, the newest model is downloaded directly.
- **Formats:** each model names the prompts it was trained on, as `shared/laya-prompts.cjs` asks them: `noul-v1` is one yes/no question per candidate answer, and `choice-v2` one question per form question that scores all its options at once, with a text box described by its label and type. The app asks a model only in its own format and refuses a decision written for another, as can happen when an update lands mid-click. The app installs only the formats it lists (`MODEL_FORMATS` in `desktop/laya-model.cjs`). A newer model in another format is ignored with the note "A newer Laya model is available, but it needs a newer version of SecondHand", and the installed model keeps working.
- **Failures:** a failed update check or update download never removes the working model. It shows next to the model's status, such as "Ready. … Update check failed: the server answered 404.", and is tried again at the next check. A download that ends early, grows past its pinned size, or does not match its SHA-256 is rejected with a message and deleted, for an update as for the first download.
- **Trust in the model repo:** updates trust the Hugging Face repo, not a signature. Whoever can write to its `main` branch (the owner's Hugging Face account, anyone who takes it over, or Hugging Face itself) can publish a `latest.json` that names different model files with matching SHA-256s, and every SecondHand with Laya on installs them within a day. The SHA-256 checks catch damaged or swapped downloads, not a bad publish. A bad model could give wrong answers, which the person reviews before any submission; a model file crafted against a bug in onnxruntime could run code as the person's account, in the model process. Signed releases, checked by the app against a key kept off Hugging Face, would close this gap; this app doesn't have them. The owner publishes with `scripts/publish-laya-model.cjs` ([docs/laya-model.md](laya-model.md#publishing-a-model)).
- **Integrity on disk:** every file is checked against its size and SHA-256 again before each load; files changed on disk are deleted and the person is asked to download again. The installed model's manifest is saved as `models/laya/installed.json` once its files are verified, and loads are checked against it. It sits next to the model, so it catches damage, not someone who can already write to the person's files. A record the app can't read or run leaves it on the shipped model, with a note.
- **Where it is stored:** under the app's data folder at `models/laya/` (on macOS `~/Library/Application Support/SecondHand/models/laya/`, on Windows `%LOCALAPPDATA%\SecondHand\models\laya\`), outside the vault. Only the installed revision is kept, plus an update while it downloads.
- **Inference is local:** the desktop app runs the model with onnxruntime-node on the CPU, in a separate utility process, so a native failure cannot take down the vault process. On a Mac with 8 or more performance cores and 16 GB or more of memory, that process runs two onnxruntime sessions, each on a worker thread of its own with half of those cores, so two batches run at once; elsewhere it runs one. Each session holds its own copy of the weights. The model is loaded on the first decision and that process is ended after 5 idle minutes, which returns its memory (with one session about 0.5 GB loaded, up to about 1.3 GB while deciding; with two about 1 GB loaded, up to about 2 GB while deciding). Each request has a timeout, and a request from an Autofill click ends when the click's 3 seconds do. Decisions make no network requests (tested with the network blocked).
- **No profile data leaves the computer:** Laya's inputs are built by desktop code from question text, candidate answers, and facts derived from the vault, and they stay in the desktop and its model process. The renderer cannot run the model. Laya's only network traffic is the update check (a plain GET of `latest.json`) and model downloads, which carry no applicant data; Hugging Face sees the computer's IP address and a `SecondHand` user agent.
- **Platforms:** the packaged apps run Laya on Windows (x64) and on Macs with Apple silicon; development builds also run it on Linux. onnxruntime-node has no Intel Mac build, so Intel Macs show Laya as unavailable and never download it.
- **Developer overrides:** `SECONDHAND_LAYA_MODEL_DIR` points the desktop app at a local export folder instead of a download, and `SECONDHAND_LAYA_MODEL_FORMAT` names its prompt format (`noul-v1` or `choice-v2`); the app won't start with a folder whose format isn't named. That folder is used as-is, without the SHA-256 pin. `SECONDHAND_LAYA_UPDATE_URL` points the update check at another `latest.json`; its files are still checked against its SHA-256s. Only unpackaged development builds accept either; a packaged app ignores them.

## What local-only means

Profile/record persistence is local. Once the user authorizes filling a field, it is exposed to the destination site and potentially other software with access to that browser page. The site may autosave before formal submission; ordinary Iowa Save and Continue sends the entered answers to Iowa. Destination servers, browser history, OS crash dumps, automatic machine backups, and third-party browser extensions are outside this application's control.

Store the vault and exported backups outside cloud-synced folders if all copies must remain offline. Use a strong password and device encryption. Windows uses `%LOCALAPPDATA%\SecondHand` rather than the roaming profile directory; macOS uses `~/Library/Application Support/SecondHand`; Linux uses the application config directory under `SecondHand`. Development tests use isolated temporary directories containing synthetic data only.

Packaged native-host tests may opt into an isolated storage root with both `SECONDHAND_TEST_MODE=1` and an absolute `SECONDHAND_TEST_USER_DATA` path below the operating system's temporary directory. This only selects local storage; the same origin, token, vault, and approval checks run. Without the explicit test mode, packaged apps use their normal storage directory.

## Verification and remaining work

Tests exercise wrong passwords and corrupted ciphertext, atomic local persistence, schema constraints, strict portal origins, bounded native frames, extension ID and bridge token validation, the autofill trust setting (dialog, Always allow, reset on a new extension ID, lock), approved-site sensitive-field confirmation, access-receipt invalidation, the exact empty-request endpoints without profile reads, and conservative adapter behavior. The real Electron smoke test exercises profile/application persistence and lock/unlock through the desktop UI, including delayed lock notifications. Native subprocess smoke messages cover the status, showApp, openApp, and field request protocol using synthetic fixtures; with the app closed, openApp starts a stand-in app that records its arguments and environment. On Windows, that stand-in is a `secondHand.exe` beside a copy of the relay, and the smoke also checks that the relay's output closes while the stand-in keeps running, so the app kept none of the relay's handles. Because the relay can only be built and run on Windows, a source test also checks that it starts nothing but that fixed executable, the way described above, in C# 5. Laya tests cover the tokenizer and prompt port against Python reference outputs, the download (checksum pass and fail, partial and oversized downloads, resume after a pause, removal), updates (the newest model on a new install, the shipped model when `latest.json` can't be read, a verified switch that waits for a running decision and deletes the old revision, ignored incompatible formats, a tampered update that leaves the installed model working, the 24-hour check), not-ready and timeout errors, the idle unload, offline decisions, and the setting at startup (on for a new install, off once turned off); with `SECONDHAND_LAYA_NOUL_MODEL_DIR` or `SECONDHAND_LAYA_CHOICE_MODEL_DIR` pointing at an export of that format, they also compare the real model's probabilities with Python's. The Electron smoke test checks that a new install downloads the model on its own from a local stand-in for the model repo, and that Laya turned off stays off after a restart. Synthetic tests and isolated subprocess checks do not establish every live portal branch or installed browser/OS combination.

This is an early pilot build, not an independently audited security product. Before public release: obtain code signing, review Chromium/Electron updates, verify the installed Windows native host with Chrome, validate actual portal fields with a consenting user, and perform an independent security review. Keep screenshots, tests, logs, issues, and commits free of real applicant data.
