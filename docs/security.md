# Security and privacy design

secondHand has no application backend. The desktop process is the sole owner of saved applicant information. It serves no HTTP endpoint. The shipped UI and extension contain no analytics, cloud AI, remote fonts, or app updater. Dependencies and build artifacts are downloaded during development/build; this is separate from applicant data processing. The only things the desktop app itself downloads are the Laya model and the file that names its newest version, and only while Laya is on. Laya is on unless the person turns it off (see [Local AI with Laya](#local-ai-with-laya)).

## Vault

`vault.secondhand` contains AES-256-GCM ciphertext with a random 96-bit nonce for every write, a 128-bit authentication tag, and version-bound authenticated additional data. Version 2 files encrypt contents with a random 256-bit data key. That key is stored only in wrapped form, in separate AES-256-GCM key slots:

- **password**: wrapped by a key derived from the user's password with a random 256-bit salt and scrypt (`N=32768`, `r=8`, `p=1`). The password must be at least 12 characters.
- **recovery**: wrapped by the same scrypt derivation of a one-time recovery key (160 random bits shown as 32 Crockford base32 characters). It is displayed once, never stored by secondHand, and replacing it removes the old slot.
- **touchId** (optional, macOS only): wrapped by an HKDF-SHA256 key from a random 256-bit key. That key is sealed with Electron `safeStorage` (the macOS Keychain) in `touch-unlock.bin` beside the vault. See [Touch ID unlock (macOS)](#touch-id-unlock-macos).

Resetting a password unwraps the data key through the recovery slot, authenticates and validates the contents, and writes a new password slot; the encrypted contents and the other slots, the Touch ID slot included, are unchanged. Only the recovery key resets a password. Someone who has neither the password nor the recovery key can only start over, which erases the saved information, or restore a backup they can open.

Earlier versions had an optional **device** slot ("Let this computer reset my password"): the data key wrapped by an HKDF-SHA256 key from a random secret sealed with `safeStorage` in `device-reset.bin`. Anyone signed in to the same operating-system account could use it to set a new password without the recovery key, so it was removed. SecondHand deletes `device-reset.bin` when it starts, still parses a `device` slot so older files and backups open, never unwraps it, and removes it at the next unlock or recovery-key reset. After a password or Touch ID unlock that removed it, the app says once that only the recovery key resets the password and offers a new one.

Version 1 files (contents keyed directly from the password) still open. Adding a recovery key upgrades them to version 2 and reuses the existing password-derived key as the password slot, so the password does not change. KDF parameters are fixed and validated when reading a backup, preventing a file from requesting arbitrary computation.

The password, recovery key, and keys are never written to settings. A copied recovery key is cleared from the clipboard after one minute if it is still there. The unlocked key is held in the desktop process and its buffer is cleared on lock. JavaScript strings and copies cannot be reliably zeroed; an unlocked machine and its memory are outside the confidentiality guarantee. The UI clears profile/application state when notified of a lock. The app locks after ten minutes without relevant activity, on system suspend, on supported OS lock-screen events, and on exit.

Writes serialize through a queue, use a private temporary file, sync that file, and atomically rename it. Unix data files are mode `0600`; Windows uses the current user's application-data directory and inherited access controls. Whole-vault size and field lengths are bounded. There is no unencrypted SQLite sidecar, journal, or document cache. Local document reading can propose text fields for review, but does not store source documents or raw OCR in the vault. Only selected details explicitly saved through the profile workflow are persisted.

Profile choices for address availability, mailing address, applicant status, programs, and medical-bill help use explicit `yes` / `no` / unanswered values. Unanswered never becomes No, and program selections do not imply eligibility. Home and mailing details remain separate. Existing encrypted profiles load with new fields unanswered, without a format migration or automatic rewrite. The fictional full-applicant test fixture is not a product default and must never be submitted to the live portal.

Encrypted export is available through the operating system's file dialog. Import requires a locked vault and explicit confirmation before replacing existing records. The prior encrypted vault is retained as a rollback file. An imported envelope is structurally validated before writing; authentication and payload validation happen when the user supplies its password or recovery key. Keep an independent backup. Losing both the password and the recovery key is not recoverable by secondHand. A backup keeps the key slots it was saved with, so an old recovery key still opens a backup made before the key was replaced.

## Library mode (Windows and macOS)

Enable **Privacy & backups → Library mode** on a shared computer. After 120 seconds without operating-system mouse or keyboard input, SecondHand deletes its local vault, import rollback copies, unfinished vault writes, Touch ID credentials and any device-reset secret left from earlier versions, and setup progress. It clears the open profile, application drafts, document review, copied recovery key (if still on the clipboard), and site-sharing approvals. Chrome activity counts; background autofill and status requests do not. The main process checks once per second, including while the app is locked or minimized.

Library mode also erases on exit, computer lock, and suspend. It remains enabled for the next patron. On startup it erases any session left by a crash before accepting requests. A separate mode marker survives settings resets; a damaged marker still enables cleanup. Failed deletion keeps access blocked, reports the error, and retries. Outstanding operations must settle and a final cleanup must finish before another session starts.

This removes app-owned files, not forensic traces or operating-system backups. It does not delete source documents, exported backups or recovery-key files, browser history, fields already filled on websites, or records held by those websites. The installed extension and downloaded AI model remain. A process that is stopped or a computer that is powered off cannot run the timer; cleanup resumes when SecondHand opens.

## Touch ID unlock (macOS)

**Unlock with Touch ID** is off by default. The setting (Privacy & backups) shows only on macOS when Electron's `systemPreferences.canPromptTouchID()` is true. Windows and Linux are unchanged; Windows Hello is out of scope.

- **Turning it on:** while unlocked, the app asks for the password again and checks it against the password slot. It makes a random 256-bit key, adds the `touchId` slot, and seals `{ version: 2, key }` with `safeStorage.encryptString` in `touch-unlock.bin`. A version 1 file, written by an earlier build of this feature, also holds when the password was last used; it still unlocks, and that time is ignored. Nothing about Touch ID is written to settings.
- **Unlocking:** the lock screen shows **Unlock with Touch ID** beside the password field. `systemPreferences.promptTouchID('unlock SecondHand')` must succeed. The app then unseals the key, unwraps the `touchId` slot and unlocks as a password unlock does: the same lock revision and access receipts, and the same idle auto-lock. A lock while the prompt is open cancels it. Two requests at once share one prompt.
- **Touch ID stays on until it's turned off.** It unlocks right after SecondHand or the Mac restarts, with no time limit and no password first. This is the project owner's choice: Touch ID must stay available whenever the applicant needs it, so a forgotten password never stands between them and their saved information. The cost is that the password no longer limits how long, or how soon after a restart, Touch ID can be used (see the limits below).
- **A password reset keeps it.** A reset with the recovery key or this computer keeps the data key and only writes a new password slot, so the `touchId` slot and `touch-unlock.bin` stay and Touch ID keeps working. SecondHand has no separate change-password action.
- **Its key and slot are removed only** when the applicant turns it off; on Start over, which erases the information; when a backup is restored, which brings a different file; and when a new password creates new information. A restored file can still carry a `touchId` slot; without its key that slot opens nothing, and the next password unlock removes it. A restore removes the key before it replaces the file, and is refused if it can't, so a Touch ID prompt already open can't unlock the backup.
- **Turning it off** removes `touch-unlock.bin`, then the slot. The password and recovery slots are never changed by Touch ID, and the password always works as the fallback.
- **Failures are shown, never hidden.** A cancelled or failed prompt says so (with macOS's reason) and leaves the password field ready. Only a damaged key file or slot turns Touch ID off: a `touch-unlock.bin` that is empty, over 4 KB, not in its format or without a 32-byte key, or a `touchId` slot that is missing or that the key doesn't open. The app names the reason on the lock screen and asks for the password. While locked, only the key can be removed; the next password unlock removes the slot. A Keychain that can't unseal the key, or a key file that can't be read, may work next time, so Touch ID stays on: the app says "Touch ID didn’t work this time" with the reason and asks for the password, and a password unlock leaves Touch ID on.
- **From Chrome:** the extension learns only `status.touchId` (`'ready'` or `'off'`) and the answer to `unlockWithTouchId`. That request carries only its id and type. The answer is `{ unlocked: true }` or `{ unlocked: false, reason }`, with `reason` `'off'` or `'cancelled'` (a cancelled prompt, or Touch ID that didn't work this time). Only a click in the side panel can send it. The app shows macOS's prompt, and no password ever passes through Chrome. When Touch ID doesn't unlock, the side panel brings SecondHand forward for the password, as it did before.

**Limits:**

- The key is in the macOS Keychain through `safeStorage`. Touch ID is checked by SecondHand's own code before it unseals the key; macOS doesn't tie the key to a fingerprint.
- Pilot builds are unsigned and run without the hardened runtime. Software running as this Mac user can run or change the app and have it unseal the key without Touch ID. Touch ID therefore protects against someone using the unlocked Mac through SecondHand's window or Chrome's side panel. It doesn't protect against malware already running as the user, or anyone who runs their own software on the signed-in account.
- Electron's prompt asks macOS for user presence (`kSecAccessControlUserPresence`). The macOS dialog also accepts this Mac account's login password instead of a fingerprint, and every fingerprint enrolled for the account works. Because Touch ID stays on with no password-first rule and no time limit, anyone who can pass that dialog can open SecondHand at any time, right after a restart included, until Touch ID is turned off. On a shared Mac account, leave it off.
- Hardware-backed biometric keys, such as a Secure Enclave key with a biometric access control that macOS itself releases only after Touch ID, need a code-signed app and a native helper. They are out of scope.
- The vault file is no weaker. The password and recovery slots still work, and the `touchId` slot is useless without the Keychain key, so a backup saved while Touch ID is on opens nothing more anywhere else. A SecondHand from before Touch ID rejects a file with a `touchId` slot as an unsupported format; turning Touch ID off before going back removes the slot.

## Desktop isolation

Only packaged local HTML/CSS/JavaScript is rendered. The window has Node integration disabled, context isolation and sandboxing enabled, spellcheck disabled, restrictive Content Security Policy, denied permissions, blocked network requests, and denied navigation/new-window requests. A narrow preload exposes named actions; the main process verifies the IPC sender, top-level frame, and exact renderer URL. The portal-opening action uses a fixed official URL.

## Local document reading

The unlocked desktop can read a user-selected PDF, PNG, or JPEG through its native file picker. It does not move, modify, or retain a copy of the original. The source-size limit is 30 MiB and the PDF limit is 12 pages. The worker bounds rendered OCR pages to 16 megapixels, rejects PNG/JPEG headers exceeding 40 megapixels, rejects image dimensions over 20,000 pixels, bounds extracted text and word output, and limits engine processing to five minutes. Per-page limits are 200,000 text characters and 12,000 words per pass; combined document limits are 500,000 text characters and 80,000 words across both passes. Native file-picker and file-opening time are separate from the engine timeout.

PDF.js, Tesseract.js, its WebAssembly runtime, and the English language model are bundled for local processing. Saved PDF annotation appearances, including filled AcroForm fields, are rendered into the OCR bitmap; no interactive annotation layer or PDF scripting is created. XFA rendering remains disabled. OCR needs no runtime network request, separately installed executable, API key, or Laya inference. Processing takes place in a hidden sandboxed Electron window with Node integration disabled, context isolation, and a dedicated temporary browser session. The session permits the fixed bundled assets and blocks network requests and other resources; navigation and new windows are not document operations.

The main process releases the source buffer, clearing bytes where possible, and destroys the worker window at completion, cancellation, or lock. The app clears temporary review text and candidates on discard, when leaving Documents, or on lock. Cancellation revokes pending results even if an operating-system picker cannot be dismissed programmatically and returns a late choice. No document database, original-file copy, or persistent OCR cache is created. As with other decrypted UI data, clearing JavaScript references cannot guarantee physical erasure of strings or operating-system memory.

Structured 1040/1040-SR, W-2, SSA-1099, and 1099-NEC candidates are layout-based suggestions requiring user review. The runtime retains automatic- and sparse-segmentation results from the same image; the parser omits SSNs, other taxpayer identifiers, and tax amounts unless both passes agree. These are correlated readings by the same model, so agreement and high OCR confidence do not establish correctness. Multiple detected tax-return or statement headers produce no profile suggestions. Selected primary-applicant details populate an unsaved profile draft; only an explicit profile Save encrypts and persists them. Historical tax year and annual amounts, spouse/dependent details, filing status, and age/blindness marks do not become current income, household members, birth dates, or eligibility answers automatically. Generic documents expose extracted text for review without assuming a tax-form layout. Reading a document neither changes the saved profile nor releases anything to the browser extension or a destination site.

The original file's own permissions, cloud sync, backups, and retention remain unchanged. OCR errors and incomplete layout support can produce incorrect or missing suggestions, so recognition is not identity verification or validation of a benefits answer. [Document OCR](document-ocr.md) describes the review flow, limits, and synthetic test scope.

The desktop's advisory [field review](field-review.md) checks a bounded copy of the current draft and document candidates without saving it. Only the exact unlocked desktop frame can request a review. Edits, cancellation, superseding requests, lock/unlock, or quitting invalidate pending results. Rule checks return fixed messages without echoing values. Optional experimental Laya feedback uses eligible printed document labels and fixed field descriptions only; source values and profile values never enter that model request. It can add warnings but cannot approve, correct, or persist data. Review does not enable or download Laya, and failures or unsupported cases leave rule results intact. No reviews or document evidence are persisted.

## Extension and local bridge

The extension uses Manifest V3, `activeTab`, `scripting`, `nativeMessaging`, and `sidePanel`. It requires Chrome 116 or newer. Its default host permission is limited to `https://hhsservices.iowa.gov/*`, and its static content script starts only on the Iowa portal path. Optional HTTPS host permissions let the user enable other sites individually, or every HTTPS site at once (see [SecondHand on all websites](#secondhand-on-all-websites)). Those sites require both Chrome's origin permission and a separate desktop trust prompt before field release; embedded forms require their own origin approval unless all websites is on. Dynamic content-script registrations and Chrome permissions can persist, but the extension has no storage permission or applicant-data persistence.

The page-hosted widget is an extension-origin iframe inside a closed shadow root, so the page cannot script it. The worker binds its requests to the iframe's own tab and accepts Autofill only from a trusted click with `confirmed: true`, or from its keyboard shortcut: Chrome sends a `chrome.commands` event only for keys the person pressed, never for a page's script, and the worker acts on the tab in front as the side panel's button would. The checklist lives in Chrome’s native sidebar. The worker accepts applicant operations only from the supported extension surfaces; content scripts and page `postMessage` calls have no direct path to the vault. Displaying either surface does not start filling. Iowa requests validate the exact HTTPS origin and portal path; other sites use their approved HTTPS origins.

The widget and sidebar receive field metadata, completion/missing/manual status, counts, and messages, never saved profile values or input values entered on the page. The one path that reads an answer typed on the page is [Save to My information](#save-to-my-information), and only after the applicant's click; that answer goes to the desktop app, not to either surface. Clicking a checklist item, the side panel's **Go to the question left** link, or the card's **questions left** link asks the content script to focus the corresponding control; it does not retrieve a saved answer. The named lists of questions filled and left, shown on other websites, carry the form's own labels, never answers. Generic mapping may send unmatched field labels, types, and choice text to Chrome's on-device AI in the extension page. It receives only allowed profile-key names, never saved answers, and has no cloud fallback. The mapper uses an already available local model rather than starting a model download. Plans and autofill results live in worker memory and clear when the tab navigates or closes, or when Chrome stops the idle worker (the next Autofill finds them again); no applicant record is written to extension storage or an application backend.

The sidebar's "What this page says" section sends a page's visible text to Chrome's on-device Summarizer in the extension page. The text leaves out form controls, their choices, SecondHand's widget, and hidden content, so it never holds a typed or saved answer. On Iowa, only the information-only screens are read. Other sites are read only after they are turned on. The Summarizer model downloads only after the applicant clicks. Page text and key points live in worker memory for the tab. Iowa screens are kept until the tab leaves Iowa or closes. There is no cloud fallback.

Chrome Native Messaging invokes a local host registered with an exact extension ID. The native host relays bounded, framed JSON over a Unix socket or Windows named pipe to the running desktop. A fresh random session token authenticates local requests; its file is readable only by the current Unix user and protected by the user's directory permissions on Windows. Requests are strictly typed and reject unknown fields. A request cannot run shell commands, access arbitrary files, or fetch arbitrary profile paths. On macOS and Linux, an `openApp` request with the app closed makes the host start SecondHand itself: its own executable (in development, with the app path), with no shell, no Chrome origin, and nothing from the request, at most once per host process. On Windows, the relay starts only the `secondHand.exe` installed in its own folder, by its full path, with no arguments, no shell, and no inherited handles (Chrome's native-messaging pipes stay with the relay), and with the relay's environment less the test-only settings, at most once per relay process.

The desktop's explicit Prepare Chrome extension action copies a fixed allowlist of bundled assets into its local `chrome-extension` folder and registers the ID derived from the manifest's public key. No vault data is copied, and no Chrome settings or enterprise policy are modified. Chrome's Developer mode / Load unpacked step remains manual. The public manifest key provides a stable development ID, not cryptographic proof of the code of an unpacked extension. Folder/clipboard IPC methods accept no arbitrary paths or clipboard payloads. A missing extension bundle does not prevent using the local vault.

The extension updates itself from that folder. Each native `status` reply names the extension build the app ships (the `BUILD` marker in its bundled `background.js`) and whether the prepared folder has it: `ready`, `failed`, or `absent`. When the folder holds another build, the app refreshes it from its own bundle with the same allowlist and checks, one refresh at a time, without registering the native host again or opening the folder. A newer build than the app's own, prepared by a newer app, is never replaced with an older one: `status` names that newer build as `ready`, and **Refresh extension files** is refused with the reason. A refresh that fails isn't retried until the person refreshes on the Chrome extension page. The `status` request carries only its ID and type, so nothing the extension sends decides what is written, and nothing is written outside that folder. The extension calls `chrome.runtime.reload()` only when the app's build is newer than its own and the `background.js` that Chrome would load from disk has that build. The app writes that file last. The reload also waits until no Autofill is on and no fill, planned fill, approval, or click is under way, and while a tab shows a need-you list or Save offers, which the reload would clear, until that tab moves on or closes. New extension files come only from the installed app, never from the network.

On Windows, a small compiled C# host relays bounded binary messages directly to the desktop's authenticated local named pipe. It does not launch Electron, open the vault, or store applicant fields. Its source is included and it uses the installed .NET Framework. This avoids Electron's Windows stdin/console behavior interfering with Chrome's length-prefixed protocol. macOS/Linux use the executable's native mode with raw descriptor streams. No global environment setting, localhost server, external runtime download, or shell command is needed by the Windows host at application runtime.

This bridge does not protect against malicious software already running as the same OS user. Such software could read process memory, the bridge token, or impersonate a local client. The native host's origin argument is an application integration check, not proof against a hostile local process.

Field release is controlled by one desktop setting, **Let Chrome autofill without asking** (`autofillWithoutAsking`), and on a site other than Iowa's portal by **Always allow on this site** (`alwaysAllowedSites`). Both are off by default.

- **Off:** each nonempty release of eligible fields shows a desktop dialog naming the destination and requested fields. A request whose fields are all held back returns no values and shows no dialog. A multi-page Iowa run can make several requests. The buttons are **Cancel**, **Allow once**, and **Always allow on this computer**. On another site, Autofill's request holds its sensitive fields back and that dialog names only the others (#176). The held fields get the "Share sensitive details?" dialog, with **Cancel** (its default), **Allow once**, and **Always allow on this site**, only when the applicant clicks [Fill sensitive details](#fill-sensitive-details) in the side panel.
- **On:** the setting is saved in `settings.json` next to the registered extension ID and separately approved site origins (at most 50, each with a host name of at most 253 characters), never in the vault. The desktop returns eligible requested values, sensitive fields included, without a dialog only while the vault is unlocked and only to that same authenticated extension ID. Iowa requests must use the allowlisted portal destination. Other HTTPS origins must be in the desktop's trusted-site list, or all websites must be on. All requested field names are allowlisted. The setting's text in the app, and the dialog that turns it on, say that it covers the SSN, birth date, income, benefits, and citizenship and disability answers on every site SecondHand is on.
- **Other-site sensitive fields:** the SSN and whether there is one, date of birth, earned/other income, where the household's income comes from (`incomeSources`), the benefits it gets now (`currentBenefits`, and every yes or no about a benefit worked out from it), assets, medical expenses, and the citizenship, disability, blindness, health and Medicare answers (`SENSITIVE_FIELDS`) are held back from Autofill on other sites unless the setting is on or the site has Always allow on this site, and get the named "Share sensitive details?" dialog only when the side panel's Fill sensitive details asks for them. Household counts are everyday fields: age-band counts (`householdCount:…`) and the adults, children and seniors counts, those worked out from members' birth dates included. The worker excludes its designated sensitive keys from optional AI guesses, never shows Chrome's on-device AI a box only the applicant answers, and refuses a guess for one.
- **Always allow on this site:** the sensitive dialog's third button saves the site's origin in `alwaysAllowedSites` in `settings.json` (at most 50, like trusted sites), for the registered extension ID only. From then on that site's requests, sensitive or not, and Laya's answers for it, are released without a dialog while the vault is unlocked and only to that extension ID. It never covers Iowa's portal, which shares its origin with other `hhsservices.iowa.gov` pages. It is dropped when the site is turned off (`untrustSite` from the extension, or Remove under the app's trusted sites), when all websites turns off and the site isn't trusted on its own, and when a different extension ID is registered; at startup, an entry for a site SecondHand isn't on is dropped. The app's Chrome extension page lists these sites under "Sites that fill sensitive details without asking", each with Remove, which needs the vault unlocked and leaves the site trusted. The app's window can only remove an entry, never add one.
- **Resetting it:** registering a different extension ID turns it off and drops every Always allow on this site. A `settings.json` that can't be read at startup resets the Chrome connection, Always allow (on this computer and on each site), the trusted sites and all websites, and the app says so when the saved information opens; only Laya's off choice is kept, when it can still be read. Locking the vault (manually, after 10 idle minutes, on suspend, on supported OS screen-lock events, or on exit) stops all releases until the user unlocks again.

Dialogs recheck the unlocked vault, the access revision, and the extension connection before releasing fields, so a lock and re-unlock while a dialog is open invalidates it. Only requested, nonblank values are returned. Native `status`, `getFields`, and `getRecordFields` responses include an `accessRevision`: a randomly seeded, process-local safe integer that changes with lock, profile, trust, or registration changes. Before a fill or supported Iowa data-page continuation, the worker checks a fresh unlocked status against its authorization receipt and rechecks the tab/document. A desktop restart invalidates earlier receipts. This is separate from the renderer's `lockRevision`, which deduplicates lock responses and notifications without discarding a newer lock.

A form embedded from another site gets its answers in its own site's name. Each `getFields`, `suggestFields`, and `answerFields` request names the site of the frame that receives the values, and each `saveFields` request names the site of the frame that holds the answer to save. The desktop's trust check and its prompts, sensitive ones included, therefore name that site and not the page around it. The worker learns each frame's address from Chrome: every frame it can reach sends it one message, and Chrome supplies the frame, its document, and its address as the sender. Nothing a page says about itself decides where a frame is. When one click fills a page and forms from other sites, each site's answers are requested, approved, and filled separately, and an embedded frame receives values only in the document Chrome placed. All receipts in one click must agree, so an Always allow chosen in a later prompt of the same click makes the person click Autofill again.

An empty `getFields` request is allowed only at the exact Iowa `enterPersonalInfo`, `addressValidation`, `dynamicQuestions`, `dynamicQuestionsStart`, and `ssaVerificationRender` endpoints, without query, fragment, or trailing slash. It runs the same unlocked/trust/consent gate, then returns empty values and an access receipt without reading the saved profile. This supports a fresh authorization for the disclosed navigation actions below, including an address page that needs no saved fields. Values from nonempty requests stay transient in the worker/content script for that fill operation and are never written to extension storage.

The trade-off is deliberate. With the setting on, anyone who can use the unlocked computer's Chrome can fill eligible saved answers, sensitive details included, into Iowa or separately approved sites (every HTTPS site while all websites is on) without a prompt, and can start the disclosed Iowa continuation actions or explicitly choose general-site Fill and continue. Always allow on this site does the same for its one site. The vault lock and the 10-minute idle lock are the boundary. The desktop cannot independently attest a Chrome tab ID or document identity: it validates the authenticated extension, the destination string, and the field names. Binding a fill to its tab is enforced by the shipped extension code, not guaranteed against hostile software controlling that extension or the same OS user. A fresh status check also cannot make a subsequent browser mutation atomic with a desktop lock.

The Iowa adapter checks known page context and exact field labels, skips hidden/ambiguous/pre-filled inputs, and rechecks element identity before filling. User-started Iowa autopilot can continue recognized information screens. It can also choose ordinary Save and Continue on the verified, complete initial applicant page, select the first verified home-address suggestion before Save and Continue on the observed address-confirmation page, and continue a fully recognized Tell Us More page only after all visible supported questions are answered and no errors or dialogs remain. The desktop approval and persistent-trust copy disclose that these actions send answers to Iowa and require the user to review the chosen address before final submission. Single-use snapshots bind the address controls, text, selection, hidden form state, URL, and document; mailing suggestions, visible county questions, errors, and visible dialogs pause automation. Address selection is a preference among Iowa's candidates, not a determination that an address is correct.

### Custom answers and general-site continuation

Custom answers are at most 50 applicant-authored `{ id, label, value, aliases, type?, options?, site? }` records encrypted inside the profile. Each label and up to five aliases is bounded to 120 characters; each answer to 1,000. They share draft/save, backup, lock, and access-revision behavior with the rest of the profile. They are never added to Laya's facts, Chrome's model prompts, native scalar projections, or settings. The extension learns only a boolean that custom answers exist and the matched values explicitly released for the current page, not the catalog.

`getCustomFields` accepts bounded question metadata on a trusted general HTTPS origin. Desktop matching uses whole labels or explicit aliases after case/whitespace/compatibility normalization and trailing colon/asterisk removal. An answer saved from a page (#186) carries its question's `type`, `options` and `site`, and matches only a question with the same words (lowercase, without accents, punctuation, a question number, or a trailing "required"), the same type, and the same set of choices; it answers a choice with the page's own option of the same words. Ambiguous saved/requested matches, an answer from a page that two questions would take, another person's scope, incompatible choices, credentials, banking/payment details, and legal confirmations are excluded. Proposed values follow `getFields`' approval rules (#186): an everyday answer gets the ordinary "Let Chrome fill this form?" dialog, listing the exact destination, questions, and answers, unless Always allow covers it, and Cancel returns no values. An answer to a question about a sensitive subject (identity numbers, birth and age, income and money, health, disability and pregnancy, citizenship and immigration, in English and Spanish) is held back unless Always allow (on this computer or on this site) covers the site: the reply names the question in `held`, nothing of it is shown, and only the side panel's Fill sensitive details asks for it again with `sensitive: true`, which gets the "Share sensitive details?" dialog for those answers alone. Until #186 every custom answer took the sensitive dialog. The worker rechecks the receipt, site, active document, and plan before placement and drops value references afterward. Custom assignments cannot replace a standard profile match, overwrite page answers, or bypass a changed label, control, option, or form binding.

The generic adapter reads native fields and open shadow roots in the current document. Root-scoped labels and ARIA references cannot borrow an identically named label from another root. Closed roots remain inaccessible. Simple contenteditable text boxes accept text, never saved HTML. Supported ARIA choices require a unique exact saved option and confirmation by the page; unconfirmed or unsupported controls remain manual. Explicit saved No is distinct from an untouched unchecked control. Existing answers are preserved.

### Remember for next time

After an Autofill on a site other than Iowa's portal, the worker keeps (in memory, for the tab, until it navigates or the site is turned off) the questions the click left open that a custom answer may fill: a text box, a date, number, email or phone box, a radio group, or a dropdown, never a checkbox, a search box, a question only the applicant answers (signatures, passwords, codes, consent, the SSN), payment details, or another person's details. File uploads and passwords are never planned at all. A question whose custom answer the app held back is never offered. For each one the side panel gets its id, its own label, whether its answer changes over time, and whether its box holds an answer now (ids in, ids out, never a value). It shows a **Remember for next time** checkbox beside each answered one, checked unless the answer changes over time, and one **Remember checked answers** button.

Only that trusted, confirmed side-panel click reads the checked boxes, one `secondhand:generic:readOpen` each, in the document Chrome placed. The engine answers only for a question in its current plan that no rule matched and that a custom answer may fill, and refuses one the page asks in more than one box. The worker then sends `rememberAnswers { url, answers: [{ label, type, options, answer }] }` for each site, in that site's own name. The desktop requires an unlocked vault and a site SecondHand is on, checks every answer as a custom answer from a page is checked, refuses one for a question only the applicant answers or for a question a custom answer typed in My information already covers, and keeps the list to 50. It shows one confirmation, "Remember these answers?", naming each question and answer (the warning form, with Cancel the default, when one is about a sensitive subject), with **Cancel** and **Remember**. After it, it rechecks the vault, the access revision, the extension ID and the site, saves only the custom answers, moves the access revision on, and tells My information that custom answers changed, never what they are. The answers go only to the app and are not kept in the extension.

**Fill and continue** is a separate explicit side-panel action for general sites. Its copy discloses that ordinary Next, Continue, or Save and Continue can transmit and save entered answers immediately. The extension retains the pre-approval one-use snapshot, including private values and hidden payload, then rechecks the active tab, unchanged same-origin page, unlocked receipt, and original controls before clicking. That private snapshot remains in the document; it is not sent to the desktop or sidebar.

Continuation requires one recognized ordinary Next, supported required answers, native validity, and no unknown widgets, page errors, unresolved embedded forms, guessed answers, visible dialogs, or protected step. Review, consent, CAPTCHA, login, signatures, certification, payments, and final submission remain manual. A semantic step attempt is consumed before the click, including an uncertain reply, so a reload cannot automatically repeat it. The run stops on a blocker and requires an explicit restart, and ends on Stop, tab switch, origin change, lock/access revocation, or its 64-step bound. One switch in the side panel, **Use SecondHand on all websites**, turns SecondHand on for every HTTPS site. The card shows only on a page with a question the rules match to a saved answer or Laya could take; search boxes, the user name or email beside a password, and verification codes don't count. Until then the app refuses origins that aren't in `trustedSites`. Sites turned on one at a time keep their registrations and stay on. Once off, nothing of SecondHand runs on other sites, and the app refuses any site it doesn't trust.

Iowa is unaffected. A kept grant turns nothing on: a site is on only while its script is registered (or `site-all` is) and the app trusts it (or `allSites` is on). It does let Chrome turn all websites on again without a second prompt.

Each site or embedded form SecondHand had on that Chrome no longer allows is then turned off the same way, with one difference: the app hears first. Without Chrome's access a registration runs nothing, so the site is off at once, and Chrome's access given back later turns nothing on by itself. When Chrome takes back `https://*/*`, all websites turns off with `untrustAllSites`, and so does every site Chrome took back with it.

Worker/content checks bind the record to one unchanged form and a unique matching owner option; no Add Another action is authorized.

### The household list

The household list (`householdMembers` in the profile) holds up to 20 people: first and last name, birth date, relationship to the applicant, and whether each is a student, with a grade. It lives in the encrypted vault with the rest of the profile and is checked by `shared/schema.cjs` like it: names are trimmed, at most 100 characters and free of control characters; birth dates are real dates not in the future; relationships and student answers come from fixed lists; a grade (at most 20 characters) is saved only for a student. The applicant is its one `self` row, which always carries their own saved name and birth date.

The list never leaves the app whole: `householdMembers` is not a field a page may ask for, and the bridge refuses it. Pages get only answers worked out from it by code in `shared/household.cjs`, ages as of the day: the household size, the adults (18–64), children (under 18) and seniors (65+) counts, age-band counts such as `householdCount:0-17` or `householdCount:60+` (whole numbers 0 to 120, read strictly by both the extension and the app), and the one student's "First Last, Grade". A count by age is answered only when every person on the list has a birth date; the student answer only when exactly one person is a student, every other person's answer is saved as No, and the grade is saved. Otherwise the question stays with the applicant. While the list has people, its counts win over the manual counts. A member's details go only into a box that asks for that member (a student's name and grade); the applicant-only guards keep them out of the applicant's own boxes, and student, child, dependent, partner, guardian, parent, and other household members' boxes never take the applicant's details. A box under another person's section heading, such as "Student information", is treated as that person's. A guardian's name is never inferred.

Laya's facts sheet gains the household's ages, the children's ages, and how many members are students, never names. It also states the applicant's student status, where the household's income comes from, the benefits it gets now, and the help the applicant wants (#184); the income and benefits facts are sensitive, as `incomeSources` and `currentBenefits` are. Facts from members' birth dates are sensitive, as the applicant's own birth date is, so an answer that needed them gets the "Share sensitive details?" prompt on other sites, naming "Household members' birth dates", unless Always allow, on this computer or on that site, covers it. The counts a page asks for by name (`getFields`) are everyday fields.

## Local AI with Laya

Laya is a decision model that helps recognize form questions. It is on by default. The Chrome extension view has one toggle, **Find more fields with Laya (runs on this computer)**, with the model's status (off, not downloaded, downloading with progress, ready, error, or no model available yet), its size, and what the last update check said, plus download, pause, and remove controls.

- **What is downloaded:** the fine-tuned Laya checkpoint exported to int8 ONNX: `model.onnx` (3.8 MB), `model.onnx.data` (421.3 MB), the tokenizer (3.6 MB), and its calibration settings, 428.7 MB (429 MB) in all for the current export. It is never bundled with the installer.
- **When:** while Laya is on, the app downloads the model in the background as soon as it starts, if the model isn't on the computer yet. This needs no unlock, because it reads and sends no saved information. A new install, or one where the person never chose, counts as on. Turning Laya off is saved and stays off: nothing is checked, downloaded, or loaded while it is off. Pause keeps the partial file; the download resumes with an HTTP range request when the person clicks Resume, or at the next start. Remove deletes the model and turns Laya off, so it isn't downloaded again until Laya is turned back on. After the download, decisions work fully offline.
- **Pinning:** `desktop/laya-model.json` pins the model the app ships with: a Hugging Face commit, a prompt format, and for every file its URL, size, and SHA-256. It is the model downloaded when nothing is installed and the update check can't be read. Downloads use https; a redirect is followed only to another https address.
- **Updates:** at startup and then every 24 hours while the app runs, and only while Laya is on, the app reads `latest.json` from the `main` branch of [huggingface.co/JacobTDang/secondhand-laya](https://huggingface.co/JacobTDang/secondhand-laya). It has the same form as `desktop/laya-model.json`: a revision, a `format`, and every file's URL (pinned to the commit that holds it), size, and SHA-256. When its revision differs from the installed one and its format is one this app can run, the new model downloads in the background into its own `models/laya/<revision>/` folder while the installed model keeps answering. An update never goes back to a revision it replaced: `models/laya/installed.json` lists those revisions, and a `latest.json` that names one is ignored with a note while the installed model keeps working. Revisions are commits, which have no order, so a rollback is published as a new commit. Only once every file matches its size and SHA-256 does the app switch to it: a decision already running finishes on the old model, the next one loads the new model, and then the old revision is deleted. An update never starts while the model is downloading, and the switch waits for running decisions. With nothing installed yet, the newest model is downloaded directly.
- **Formats:** each model names the prompts it was trained on, as `shared/laya-prompts.cjs` asks them: `noul-v1` is one yes/no question per candidate answer, and `choice-v2` one question per form question that scores all its options at once, with a text box described by its label and type. The app asks a model only in its own format and refuses a decision written for another, as can happen when an update lands mid-click. The app installs only the formats it lists (`MODEL_FORMATS` in `desktop/laya-model.cjs`). A newer model in another format is ignored with the note "A newer Laya model is available, but it needs a newer version of SecondHand", and the installed model keeps working.
- **Failures:** a failed update check or update download never removes the working model. It shows next to the model's status, such as "Ready. … Update check failed: the server answered 404.", and is tried again at the next check. A download that ends early, grows past its pinned size, or does not match its SHA-256 is rejected with a message and deleted, for an update as for the first download. A failed update check deletes nothing, so an update download left from before a restart is kept; the next check that works resumes or deletes it. When the disk is full, the download or install stops with "The Laya model couldn’t be saved on this computer (ENOSPC). Free some space and try again." The working model keeps answering.
- **Trust in the model repo:** updates trust the Hugging Face repo, not a signature. Whoever can write to its `main` branch (the owner's Hugging Face account, anyone who takes it over, or Hugging Face itself) can publish a `latest.json` that names different model files with matching SHA-256s, and every SecondHand with Laya on installs them within a day. The SHA-256 checks catch damaged or swapped downloads, not a bad publish. A bad model could give wrong answers, which the person reviews before any submission; a model file crafted against a bug in onnxruntime could run code as the person's account, in the model process. Signed releases, checked by the app against a key kept off Hugging Face, would close this gap; this app doesn't have them. The owner publishes with `scripts/publish-laya-model.cjs` ([docs/laya-model.md](laya-model.md#publishing-a-model)).
- **Integrity on disk:** every file is checked against its size and SHA-256 again before each load; files changed on disk are deleted and the person is asked to download again. The installed model's manifest is saved as `models/laya/installed.json` once its files are verified, and loads are checked against it. It sits next to the model, so it catches damage, not someone who can already write to the person's files. A record the app can't read or run leaves it on the shipped model, with a note.
- **Where it is stored:** under the app's data folder at `models/laya/` (on macOS `~/Library/Application Support/SecondHand/models/laya/`, on Windows `%LOCALAPPDATA%\SecondHand\models\laya\`), outside the vault. Only the installed revision is kept, plus an update while it downloads.
- **Inference is local:** the desktop app runs the model with onnxruntime-node on the CPU, in a separate utility process, so a native failure cannot take down the vault process. On a Mac with 8 or more performance cores and 16 GB or more of memory, that process runs two onnxruntime sessions, each on a worker thread of its own with half of those cores, so two batches run at once; elsewhere it runs one. Each session holds its own copy of the weights. The model is loaded on the first decision and that process is ended after 5 idle minutes, which returns its memory (with one session about 0.5 GB loaded, up to about 1.3 GB while deciding; with two about 1 GB loaded, up to about 2 GB while deciding). Each request has a timeout, and a request from an Autofill click ends when the click's 3 seconds do. Decisions make no network requests (tested with the network blocked).
- **No profile data leaves the computer:** Laya's inputs are built by desktop code from question text, candidate answers, and facts derived from the vault, and they stay in the desktop and its model process. The renderer cannot run the model. Laya's only network traffic is the update check (a plain GET of `latest.json`) and model downloads, which carry no applicant data; Hugging Face sees the computer's IP address and a `SecondHand` user agent.
- **Best guesses (#185), off (#189):** the desktop never asks Laya for a best guess, so `answerFields` returns sure answers only, on every site. On the 15-form final holdout most guesses were wrong: round 2's model got 0 of 4 right and round 4's 2 of 8 (`ML_model/eval/reports/*-final-app-fills.json`). `createFieldAnswers` keeps the ability, from the everyday facts only and never for a checkbox group or a question naming a sensitive detail (`SENSITIVE_QUESTION` in `shared/laya-prompts.cjs`), so `ML_model/eval/app_accuracy.cjs` can measure a future model. The extension still checks guesses from a desktop that sends them (0.5.0 does, off Iowa's portal): the worker refuses a reply with a guess for a question it didn't send, a checkbox group, an option the question lacks, a question Laya also answered, or on Iowa's portal, and fills nothing from it; the page engine refuses a guess in a checkbox group or on Iowa's portal. Such a guess is filled with a dotted plum outline, apart from a sure answer's dashed amber one, and the side panel lists each guessed question's own label; the worker keeps that list in memory for the tab, never the chosen option, and forgets it when the tab navigates or closes.
- **Questions in other languages:** Laya reads English. Before it sees a question, the extension's service worker reads the question's language with Chrome's built-in LanguageDetector, or with the language the page declares when the detector isn't ready, and translates the label and options to English with Chrome's built-in Translator, on this computer. Only the page's question text goes to the translator, never a saved answer. Laya's answer is filled as the page's own option at the same position. A question whose language can't be told, or that Chrome can't translate (no translator, a language not downloaded, a translation that isn't clear), stays with the person, and the result says why. The worker never starts a translator download.
- **Platforms:** the packaged apps run Laya on Windows (x64) and on Macs with Apple silicon; development builds also run it on Linux. onnxruntime-node has no Intel Mac build, so Intel Macs show Laya as unavailable and never download it.
- **Developer overrides:** `SECONDHAND_LAYA_MODEL_DIR` points the desktop app at a local export folder instead of a download, and `SECONDHAND_LAYA_MODEL_FORMAT` names its prompt format (`noul-v1` or `choice-v2`); the app won't start with a folder whose format isn't named. That folder is used as-is, without the SHA-256 pin. `SECONDHAND_LAYA_UPDATE_URL` points the update check at another `latest.json`; its files are still checked against its SHA-256s. Only unpackaged development builds accept either; a packaged app ignores them.

## What local-only means

Profile/record persistence is local. Once the user authorizes filling a field, it is exposed to the destination site and potentially other software with access to that browser page. The site may autosave before formal submission; ordinary Iowa Save and Continue sends the entered answers to Iowa. Destination servers, browser history, OS crash dumps, automatic machine backups, and third-party browser extensions are outside this application's control.

Store the vault and exported backups outside cloud-synced folders if all copies must remain offline. Use a strong password and device encryption. Windows uses `%LOCALAPPDATA%\SecondHand` rather than the roaming profile directory; macOS uses `~/Library/Application Support/SecondHand`; Linux uses the application config directory under `SecondHand`. Development tests use isolated temporary directories containing synthetic data only.

Packaged native-host tests may opt into an isolated storage root with both `SECONDHAND_TEST_MODE=1` and an absolute `SECONDHAND_TEST_USER_DATA` path below the operating system's temporary directory. This only selects local storage; the same origin, token, vault, and approval checks run. Without the explicit test mode, packaged apps use their normal storage directory.

The Electron UI smoke stands in for Touch ID and the Keychain with `SECONDHAND_TEST_TOUCH_ID=approve`. It is accepted only together with `SECONDHAND_TEST_MODE=1`, so the app's data is in a temporary folder. Then the prompt always succeeds and the key is sealed with a plain, reversible encoding, never the Keychain. A packaged app given it refuses to start, and the native host drops it, as it drops the other test settings, when it starts the app.

Laya tests cover the tokenizer and prompt port against Python reference outputs, the download (checksum pass and fail, partial and oversized downloads, resume after a pause, removal), updates (the newest model on a new install, the shipped model when `latest.json` can't be read, a verified switch that waits for a running decision and deletes the old revision, ignored incompatible formats, a tampered update that leaves the installed model working, the 24-hour check), not-ready and timeout errors, the idle unload, offline decisions, and the setting at startup (on for a new install, off once turned off); with `SECONDHAND_LAYA_NOUL_MODEL_DIR` or `SECONDHAND_LAYA_CHOICE_MODEL_DIR` pointing at an export of that format, they also compare the real model's probabilities with Python's. The Electron smoke test checks that a new install downloads the model on its own from a local stand-in for the model repo, and that Laya turned off stays off after a restart. Touch ID tests run the real main process and vault with Touch ID, the Keychain and the clock simulated. They cover turning it on and off, unlocking, Touch ID right after a restart and with no time limit, keys sealed in the earlier format, a cancelled prompt, a lock during the prompt, damaged or mismatched keys, resets that keep it, Start over, restored backups, the extension's request, and the test hook. The Electron smoke test turns Touch ID on with the test hook, locks as a screen lock does, unlocks with Touch ID, and checks that it is ready at once after a restart, that a reset keeps it, and that Start over removes it. A real Touch ID prompt is checked by hand. Synthetic tests and isolated subprocess checks do not establish every live portal branch or installed browser/OS combination.

This is an early pilot build, not an independently audited security product.
