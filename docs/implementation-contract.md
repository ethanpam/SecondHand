# Internal implementation contract

Runtime: Electron desktop, plain HTML/CSS/JavaScript renderer, Manifest V3 Chrome extension. No application backend or cloud AI. CommonJS desktop modules (`.cjs`); browser scripts are plain JS. Node test runner.

## Desktop renderer API

`window.secondHand` exposes async methods returning plain values or throwing sanitized errors:

- `status()` -> `{ exists, unlocked, lockRevision, recoveryKey, deviceReset, deviceResetSupported, extensionId, autofillWithoutAsking, trustedSites, allSites, touchId, touchIdSupported, touchIdNotice, bridgeRunning, platform, extensionSetup }`; setup contains `{ directory, extensionId, version, build, exists, prepared, newerCopy }`, or `{ prepared: false, available: false }` if bundled assets are unavailable. `newerCopy` is the build of a whole copy a newer app prepared in the folder, which this app never replaces with its own older build (#142), or null. `touchId` is `'ready'` or `'off'`: once on, Touch ID stays ready until it's turned off, with no password-first rule after a restart and no time limit (the owner's choice; see [security](security.md#touch-id-unlock-macos)); `touchIdSupported` is true only on macOS when `canPromptTouchID()` is; `touchIdNotice` says why Touch ID was turned off, or is null; `settingsNotice` says what was reset when `settings.json` couldn't be read at startup, or is null

- `createVault({ password, allowDeviceReset })` -> `{ status, recoveryKey, deviceResetFailed }`; the recovery key is returned once and never stored
- `unlock(password)` -> status
- `resetPassword({ recoveryKey, password } | { method: 'device', password })` -> status (unlocked with the new password; Touch ID stays on, since the data key is unchanged)
- `startOver({ confirmation })` -> status (locked only; `confirmation` must be the typed phrase `start over`). Erases the encrypted file, copies kept by earlier restores, and the reset secret for this computer, and Touch ID's key; Chrome extension settings stay. `status.exists` is then false, so a new password can be created
- `replaceRecoveryKey()` -> `{ recoveryKey }` (unlocked only; retires the previous key)
- `setDeviceReset(enabled)` -> status (unlocked only)
- `setTouchIdUnlock({ enabled: true, password } | { enabled: false })` -> status (unlocked only). Turning Touch ID on checks the password; see [security](security.md#touch-id-unlock-macos)
- `unlockWithTouchId()` -> status (unlocked), or throws why not: Touch ID is off, the prompt was cancelled, or Touch ID was turned off and why
- `saveRecoveryKey(recoveryKey)` -> `{ cancelled }` / `copyRecoveryKey(recoveryKey)` -> true
- `lock()` -> status
- `getData()` -> `{ profile, applications }`
- `saveProfile(profile)` -> saved profile
- `setupProgress()` -> `{ step, steps: 6 }` or `null` (unlocked only). The guided first-run setup's progress: how many of its six steps are done, or `null` when no setup is under way. An unreadable progress file fails with an error.
- `startSetup()` -> `{ step: 0, steps: 6 }` (unlocked only). The renderer calls it right after `createVault`, then offers the setup once the recovery key is saved.
- `saveSetupProgress(step)` -> `{ step, steps: 6 }` or `null` (unlocked only; `step` a whole number 0 to 6). Steps done never go down; 6 finishes the setup and removes its progress file. Refused when no setup is under way. Progress lives in `setup-progress.json` (`{ version: 1, step }`) beside `settings.json`, never in the vault, and a restored backup removes it.
- `onProfileChanged(callback)` -> unsubscribe function; the callback receives `{ fields }`, the names of the saved fields a `saveFields` request changed, never their values
- `saveApplication(application)` -> saved application (empty/missing id creates UUID)
- `deleteApplication(id)` -> true
- `openPortal()` -> true (fixed Iowa URL only)
- `openExtensionGuide()` -> true (opens SecondHand's fixed `/chrome-extension` guide; in development only, `SECONDHAND_WEBSITE_URL` can point it at a local http(s) website)
- `prepareExtension()` -> `{ directory, extensionId, version, prepared, manifestPath, folderOpened }`; copies bundled assets into the fixed local extension folder and registers its stable ID; never installs into Chrome
- `openExtensionFolder()` / `copyExtensionFolderPath()` -> true (fixed prepared folder only)
- `copyChromeExtensionsUrl()` -> true (copies the fixed `chrome://extensions` address)
- `connectExtension(extensionId)` -> `{ extensionId, manifestPath }` (register native host for current OS)
- `removeTrustedSite(origin)` -> status (unlocked only; removes an exact previously approved origin, and Always allow on it).
- `removeAlwaysAllowedSite(origin)` -> status (unlocked only; takes back Always allow on an exact origin in `alwaysAllowedSites`, which stays trusted). The app can only remove one: only the sensitive dialog adds it.
- `turnOffAllSites()` -> status (unlocked only; clears `allSites`). The app can only turn all websites off: Chrome's prompt comes from the extension.
- `setAutofillTrust(enabled: boolean)` -> status. Stores `autofillWithoutAsking` with `extensionId`, separately approved `trustedSites`, and `alwaysAllowedSites` (saved only while it has any) in the non-sensitive `settings.json`, never in the vault. Requires an unlocked vault. Status carries `alwaysAllowedSites` too.
- `exportBackup()` / `importBackup()` -> `{ cancelled: boolean }` (native dialogs, encrypted vault bytes only; import only while locked, and it turns Touch ID off: the restored file is a different one)
- `onLocked(callback)` -> unsubscribe function; the callback receives `{ lockRevision }` (invalid or legacy notifications provide no revision and still clear sensitive UI)
- `onUnlocked(callback)` -> unsubscribe function; called with `{ lockRevision }` when the side panel's `unlockWithTouchId` unlocked SecondHand, so the window reads status and shows the saved information

`lockRevision` is a monotonic, process-local counter used to correlate a lock response with its notification. The renderer applies a transition once, regardless of their delivery order, so a delayed duplicate notification cannot erase a newly typed passphrase or authentication error. A newer lock transition must still clear sensitive UI and invalidate pending data loads. The counter is not an applicant field or persisted vault data.

Profile is a flat object of optional string fields, allowlisted by `shared/schema.cjs`, plus one list, `householdMembers`:

- Identity: firstName, middleName, lastName, suffix, maidenName, isApplicant, birthDate (YYYY-MM-DD), ssn.
- Contact: email, phone (reference only, not automatically assigned a type), homePhone, mobilePhone, bestContactTime (at most 30 characters).
- Home: hasHomeAddress, addressLine1, addressLine2, city, state, zip, county.
- Mailing: mailingSameAsHome, mailingAddressLine1, mailingAddressLine2, mailingCity, mailingState, mailingZip.
- Explicit requests: programSnap, programFip (FIP or RCA), programMedicaid, helpPayMedicalBills (the portal asks about the last three calendar months).
- Household and preparation notes: householdSize, monthlyEarnedIncome, monthlyOtherIncome, monthlyRent, monthlyUtilities, householdAdults, householdChildren, householdSeniors, householdVeteran, householdDisability, assetsOnHand, monthlyMedicalExpenses, householdAllCitizens, householdLegalStatus, householdPregnant, householdMedicare.
- The applicant's own answers to Iowa's Tell Us More questions: sex, maritalStatus, hasSsnAnswer, ssnCardNameMatches, usCitizen, militaryOrVeteran, disabled, blind, healthLimitation, medicare.
- The household list (#98): `householdMembers`, an array of up to 20 `{ id, firstName, lastName, birthDate, relationship, student, grade }`. `id` is a UUID, unique in the list. Names are trimmed, at most 100 characters; `birthDate` is blank or a real YYYY-MM-DD date; `relationship` is blank or one of `self`, `spouse-partner`, `child`, `parent`, `sibling`, `grandchild`, `other-relative`, `other`; `student` is blank, `yes`, or `no`; `grade` is at most 20 characters and only for a student. Every person but the applicant needs a first name. A nonempty list has exactly one `self` row, which always takes the applicant's own `firstName`, `lastName`, and `birthDate`. Profiles without the list read it as `[]`.

Birth dates (#135): a save (`saveProfile`, `saveFields`) refuses the applicant's or anyone's birth date that is after today or more than 130 years ago, naming whose it is ("Your" or "Person 3’s", as My information numbers its rows). Today is this computer's own date, in its own timezone, never the UTC date (`shared/household.cjs` `localDate`). A profile read back from the vault (`validateStoredProfile`) does not check birth dates against today, so a clock set back, or a date saved before the 130-year limit, never keeps the information from opening. Such a stored date is never filled into a page and gives no age: answers worked out from it stay with the applicant, and the reply says why (`reason`, below). While one is saved, `saveFields` is refused with whose date it is and to fix it in My information. The Iowa adapter fills a date of birth only under the same rule, on the same local date. Development tests may pin today with `SECONDHAND_TEST_TODAY` (YYYY-MM-DD), which needs `SECONDHAND_TEST_MODE=1` and is refused by a packaged app.

`hasHomeAddress`, `mailingSameAsHome`, `isApplicant`, the four request fields, and the household Yes/No fields listed in `YES_NO_FIELDS` accept only `''`, `'yes'`, or `'no'`. An explicit `'no'` is a real answer and is released when approved; `''` is unknown and omitted from field responses. Programs are independent user choices, not eligibility determinations. `suffix` accepts blank, I through X, Jr., or Sr. `sex` accepts blank, Male, or Female, and `maritalStatus` blank or one of Iowa's choices: Divorced, Legally Separated, Married (includes common-law), Never Married, Separated, Widowed. A saved `ssn` with `hasSsnAnswer` `'no'` is rejected. All other values remain bounded strings. No field defaults, boolean coercion, inferred programs, copied mailing addresses, or inferred address answers are permitted. Old encrypted profiles normalize absent new keys to blank in memory; opening them does not rewrite the vault. The profile payload remains version 1. New encrypted vaults use the version 2 envelope with password/recovery key slots; legacy version 1 envelopes remain readable.

While `householdMembers` has people, `householdSize`, `householdAdults` (18–64), `householdChildren` (under 18) and `householdSeniors` (65+) are worked out from it, ages as of today, and win over the saved manual counts; an age count needs every person's birth date, usable on today, and is otherwise blank. My information shows those counts read-only, and names whose birth date keeps them blank. `shared/schema.cjs` `releasedValue(profile, field)` is the one place a released answer is worked out: saved fields as saved, `hasSsn`, `studentNameGrade` (the one student's "First Last, Grade", only when exactly one person is a student, every other person's answer is No, and the grade is saved), the list's counts, and age-band counts `householdCount:L-H` or `householdCount:N+` (whole numbers 0 to 120 without leading zeros, L ≤ H), counted from birth dates only. `householdMembers` itself is never released.

Saved profile fields are broader than live autofill coverage. The Iowa adapter requests only its verified page-scoped keys: 25 initial applicant keys, birthDate on the separately scoped primary-applicant Tell Us More page, and on its `dynamicQuestionsStart` layout the applicant's own Tell Us More answers plus the household citizenship, disability and Medicare answers that can settle a question the applicant left blank. `hasSsn` is worked out by the desktop (Yes when an SSN is saved, else the saved `hasSsnAnswer`) and never carries the number. SSN, email, county, the other household notes and money notes are not mapped by that verified Iowa adapter. The generic engine may map some of them on other pages, subject to its own rules and native approval; this does not establish Iowa-specific coverage. Tell Us More never auto-advances. The schema-valid `tests/fixtures/applicant-profile.json` is entirely fictional; automated tests keep it isolated. A separately authorized manual live inspection is recorded in `docs/iowa-live-journey.md` and stopped before signing or submitting.

Applications: `{ id, program: 'Iowa SNAP', status, createdAt, updatedAt, confirmationNumber, notes, nextAction, dueDate }`. Allowed status: draft, in_progress, submitted, needs_action, approved, denied. Submitted requires confirmationNumber. Manual user records clearly labeled. No invented deadlines.

## Native bridge protocol (extension ↔ host)

Host name `org.secondhand.bridge`. Each request `{ id: string, type, ...payload }`. Response `{ id, ok: true, data }` or `{ id, ok: false, error: string, code? }`. The only codes are `LAYA_NOT_READY` and `DESKTOP_UNREACHABLE`. The macOS/Linux host answers `DESKTOP_UNREACHABLE` when it can't reach the running desktop app; the Windows relay and older hosts send the same failure without the code, and the extension treats both as the app being closed.

- `status` -> `{ unlocked, applicationCount, accessRevision, allSites, laya: { state }, extension, touchId }` (no profile values). When `allSites` isn't `true`, the extension turns all websites off in Chrome. `state` is `off`, `unavailable`, `not-downloaded`, `downloading`, `ready`, or `error`. `touchId` is `ready` or `off`.
- `unlockWithTouchId` -> `{ unlocked: true }` or `{ unlocked: false, reason: 'off' | 'cancelled' }` (#99). Carries only `id` and `type`. When SecondHand is locked and Touch ID is ready, the app shows macOS's Touch ID prompt and unlocks as a password unlock does. Nothing else about Touch ID, and never a password, passes through Chrome.
- `showApp` -> `{ shown: true }`. Shows and focuses the desktop window so the user can unlock. Works while locked and returns no profile data.
- `openApp` -> `{ opened: 'shown' | 'launched' }`. Carries only `id` and `type`. The macOS/Linux native host handles it itself: it relays `showApp`, and a running app comes forward (`shown`). If the app can't be reached, the host starts SecondHand (`launched`): its own executable, detached with no output, with no arguments when packaged and with the app path in development, never with Chrome's origin or anything from the request. It keeps `SECONDHAND_USER_DATA` and drops test-only settings. One start per host process; a failed start answers `SecondHand could not be started (CODE).` The Windows relay passes `openApp` on unchanged to a running app, which answers `shown`. If the app can't be reached (no bridge session, an unreadable one, or no app answering on its pipe), the relay starts `secondHand.exe` from its own folder (`launched`): no arguments, none of the relay's handles, the relay's environment less the test-only settings, and nothing from the request. It too starts the app at most once per relay process, and a failed start answers `SecondHand could not be started (Windows error N).` Chrome starts a host for each request, so two quick clicks can start the app twice; the desktop's single-instance lock keeps one running.
- `getFields` `{ url, fields: string[], sensitive?: true }` -> `{ values: { field: value }, accessRevision, held?: string[], reason? }`. `reason: 'birthDate'` when a requested answer was left out because a saved birth date it needs is after today or more than 130 years ago; the side panel says so with the fill's result. Requires an unlocked vault and the approved extension ID. Fields are the schema's request fields (`householdMembers` excluded, `hasSsn` and `studentNameGrade` included) and up to 20 age-band keys (`householdCount:0-5`, `householdCount:60+`), each answered as `releasedValue` works it out. Iowa requests use the exact HTTPS origin and portal path. Other HTTPS sites additionally require an explicitly trusted origin, or `allSites` on. Fields are strictly allowlisted, and only requested nonblank values are returned.
  - When `autofillWithoutAsking` is on and the caller's extension ID matches the stored one, eligible requests return without a dialog, sensitive fields included (#175). So do requests from a site in `alwaysAllowedSites`, for that extension ID; Iowa's portal never follows that list.
  - Otherwise a desktop dialog names the fields, with the buttons **Cancel**, **Allow once**, and **Always allow on this computer**. "Always allow" turns the setting on and saves it.
  - The dialog rechecks the unlocked vault, the access revision, and the extension ID before releasing values, so a lock and re-unlock while it is open invalidates the answer.
  - Registering a different extension ID turns the setting off and empties `alwaysAllowedSites`.
  - Other sites require desktop `trustSite` approval and Chrome’s optional origin permission. On those sites, when the request would need a dialog, Autofill's request holds its `SENSITIVE_FIELDS` fields back (#176): the dialog above names only the others (and none shows when every field asked for is sensitive), the reply carries only their values, and `held` names the sensitive fields in request order. Nothing is read for a held field, and `reason` speaks only for the fields released. `held` is absent when nothing was held back: always on Iowa's portal, and whenever Always allow (on this computer or on this site) covers the request.
  - `sensitive: true` is the side panel's **Fill sensitive details** (#176). It asks for held fields alone: every field must be in `SENSITIVE_FIELDS`, and the URL may not be Iowa's portal (the bridge refuses `sensitive` with any other value, on Iowa's portal, or as an empty navigation request; the desktop refuses an everyday field with "Only sensitive details on a site other than Iowa’s application are asked for this way."). Nothing is held back from it. Unless Always allow covers the site, it gets the "Share sensitive details?" dialog for those fields alone, with **Cancel** (the default), **Allow once**, and **Always allow on this site**, and Cancel refuses it with "You cancelled this field request." Always allow on this site adds the origin to `alwaysAllowedSites` (at most 50; the 51st is refused with the reason) and saves it, moving `accessRevision` on. Household counts are not sensitive: age-band keys, and `householdAdults`, `householdChildren` and `householdSeniors`, those worked out from the household list included.
  - `alwaysAllowedSites` loses a site on `untrustSite` or `removeTrustedSite` for it, loses every site not in `trustedSites` when all websites turns off, and empties when a different extension ID is registered. At startup it keeps only https origins SecondHand is on, and only with a valid saved extension ID.
  - An empty `fields: []` is accepted only for the exact observed Iowa `enterPersonalInfo` or `addressValidation` URL, with no query, fragment, or trailing slash. It authorizes the disclosed verified applicant continuation or first-home-suggestion action under the same unlocked/trust checks and returns `{ values: {}, accessRevision }` without reading the saved profile.
- `saveFields` `{ url, fields: { key: value } }` -> `{ saved: string[] }` (#98, Save to My information). The URL rules mirror `getFields`: any HTTPS site at the bridge, then a trusted origin, `allSites`, or Iowa's portal at the desktop. Keys come from `SAVE_FIELDS` (the general engine's `PROFILE_KEYS` less `ssn`); each value is a nonblank string of at most 200 characters that passes the page-text rule, and the merged profile must pass `validateProfile`. The page-text rule (`UNSEEN` in `desktop/bridge.cjs`) refuses text with a character that reorders, hides, or breaks the words around it: a control character (C0, DEL, C1), a format character (bidi controls such as U+202E, zero-width characters, tag characters), a line or paragraph separator (U+2028, U+2029), or another default-ignorable character (variation selectors, the soft hyphen, fillers). U+200C ZERO WIDTH NON-JOINER and U+200D ZERO WIDTH JOINER are allowed, because Persian, Arabic, and Indic words need them. Such text is refused, never stripped, so a desktop dialog shows only the page's own text. Requires an unlocked vault. Only blank fields are saved: an answer already saved, or a household count while the household list sets it, is refused with the reason. One desktop confirmation, "Save to My information?", names each field and value with **Cancel** and **Save** (the warning form, Cancel by default, for sensitive fields); there is no Always allow. It shares the one-approval-at-a-time guard and rechecks the unlocked vault, the access revision, and the extension ID after the dialog. A save moves `accessRevision` on and sends the renderer the changed field names. The extension sends it only from a trusted side-panel click, after reading that one box (see below).
- `trustSite` `{ url }` -> `{ trusted: true, origin }`; a native desktop prompt approves a non-Iowa HTTPS origin before adding it to the local trusted-site list.
- `untrustSite` `{ url }` -> `{ trusted: false, origin }`. Removes an HTTPS origin from the trusted-site list, and from `alwaysAllowedSites`, when the extension turns that site (or an embedded form) off; needs no unlock or prompt.
- `trustAllSites` -> `{ allSites: true }`. Carries only `id` and `type`. Requires an unlocked vault; one desktop prompt approves every HTTPS site and saves `allSites` in `settings.json`. Sensitive fields follow `getFields`' other-site rule on each site.
- `untrustAllSites` -> `{ allSites: false }`. Carries only `id` and `type`. Clears `allSites`, and drops from `alwaysAllowedSites` every site not in `trustedSites`; needs no unlock or prompt.
- `recordProgress` `{ url, filledCount: integer }` -> `{ recorded: true }`. Updates a draft/in_progress Iowa application, no page HTML, no profile values, no inferred submitted/approved status. Requires unlocked vault.
- `warmLaya` -> `{ state }` (#39, #42). When an Autofill click starts on a page with questions Laya may see, the desktop loads Laya's model (its first load after idle takes seconds) before the click's Laya budget starts, then answers with Laya's state. A model that fails to load answers `error`. Reads no saved answers and needs no unlock.
- `suggestFields` `{ url, fields: [{ id, label, type, options }], budgetMs }` -> `{ suggestions: { [id]: key } }` (#39). Laya matches text boxes to saved fields. Up to 40 fields of type `text`, `textarea`, `number`, `date`, `email`, or `tel`; labels up to 200 characters; up to 30 options of up to 100 characters. Labels and options pass the page-text rule (see `saveFields`). The extension (`layaQuestion` in `extension/generic-adapter.js`) leaves a question that breaks it to the applicant and never sends it, so one such question can't make the bridge refuse the rest. Questions carry labels and options only, never saved answers. Keys are never SSN or another saved answer AI may not guess. It returns keys only and needs no approval: their values come through `getFields`, which asks.
- `answerFields` `{ url, questions: [{ id, label, type, options }], budgetMs }` -> `{ answers: { [id]: optionText }, guesses: { [id]: optionText }, accessRevision, reason? }` (#42, #185). `reason: 'birthDate'`, as for `getFields`, when a question was left with neither an answer nor a guess and the facts sheet had no age from a saved birth date it can't use. Laya answers `radio`, `select`, and `checkbox` questions from a facts sheet built from the saved profile inside the desktop app; the sheet never leaves it. Up to 30 questions, same label and option limits.
  - `guesses` (#185) are Laya's best guesses, off Iowa's portal only: for a `radio` or `select` question with no sure answer that isn't about a sensitive detail (`sensitiveQuestion` in `shared/laya-prompts.cjs`), its top-scoring option from the everyday facts, when that option beats the abstain candidate and no other option ties it. A question is in `answers` or `guesses`, never both; on Iowa's portal `guesses` is always empty. A desktop from before #185 sends no `guesses`, which the extension reads as none. The extension refuses a reply whose guesses name a question it didn't send, a `checkbox` question, an option the question lacks, a question also in `answers`, or any guess on Iowa's portal. It fills a guess with the engine's `laya-guess` mark, counts it in the result as `layaGuessed`, and lists `layaGuesses: [{ id, label }]` for the side panel.
  - Answers and guesses are profile information, so they follow `getFields`' approval, guesses listed beside the answers with "(a guess)" after each and treated as answers that needed no sensitive fact: with Always allow on (or the site in `alwaysAllowedSites`) and the stored extension ID, they are returned with no dialog, those that needed a sensitive fact included. Otherwise one dialog lists each question with the option that would be filled, with Cancel, Allow once, and Always allow. When an answer needed a sensitive fact, that same single dialog is the "Share sensitive details?" one with Cancel, Allow once, and Always allow on this site. Cancel there drops only the answers that needed a sensitive fact, and a second "Let Chrome fill this form?" dialog lists only the others. Cancel on that dialog, or on a dialog with no sensitive answers, returns no answers, and a lock or access change while a dialog is open returns none. Iowa's portal follows `getFields`' Iowa rule, with no sensitive dialog. The dialogs share `getFields`' one-approval-at-a-time guard.
  - Both need Laya ready (otherwise they fail with `code: 'LAYA_NOT_READY'` and the extension fills as it does without Laya), a trusted HTTPS site or Iowa's portal, and an unlocked vault. Questions only the applicant answers are never scored: signatures and initials, texted, emailed or verification codes, security questions, usernames, consent, attestation, agreements, terms, and SSN (`UNSAFE_QUESTION`, identical in `extension/generic-adapter.js` and `shared/laya-prompts.cjs`). The confidence bars (0.9 to answer, 0.95 to match, and a clear lead over the runner-up) are in `desktop/laya-decisions.cjs`.
  - Each Autofill click gives Laya 3 seconds in all. The extension asks `suggestFields` first, then `answerFields` with what is left (#90): a text box's candidates are short saved-field descriptions, while each of a choice question's carries the facts sheet, so text boxes take a fraction of the time and a long checklist can't starve them. It sends what the click has left as `budgetMs`, a whole number from 1 to 3000; only time spent waiting on Laya counts, never the applicant's time in an approval dialog. The desktop decides question by question until that deadline and drops any decision made after it; what is left goes to "need you". With a `noul-v1` model it answers the choice questions with the fewest options first, in groups by batches through the model, each group through both of its passes, so long checklists come last.
  - Answers come before `getFields`. An Always allow in `getFields`' dialog outdates their access receipt, so the extension fills none of them and asks for another click; an answer set with nothing to fill is ignored.

Iowa portal URL: `https://hhsservices.iowa.gov/apspssp/ssp.portal`. Exact origin `https://hhsservices.iowa.gov`; path must be `/apspssp/ssp.portal` or descendants, no username/password/other ports.

`accessRevision` is a randomly seeded, process-local safe-integer disclosure revision, separate from the renderer’s `lockRevision`. A fill/Next rechecks that the desktop is unlocked and the revision still matches its field authorization before acting. Lock, profile changes, or connection/trust changes invalidate prior authorization.

The bridge supplies the desktop handler with `{ extensionId }` from the authenticated native envelope; request payloads cannot override this context. The desktop cannot attest Chrome tab IDs, so the extension binds every autofill to the tab that asked for it and re-checks that tab's URL before each fill pass.

Native host relays to running desktop over authenticated local IPC, not HTTP. Desktop is sole vault owner. The extension fills approved mapped fields. Iowa autopilot can continue verified information screens, the complete initial applicant page, and the verified first-home-address confirmation; other navigation stays manual. It never signs or submits an application. Unknown sections, unanswered questions, signatures, consent, review, passwords, CAPTCHA, MFA, and file inputs stay manual. On other pages the general engine never guesses or fills a box only the applicant answers, whether from its rules, Laya, or Chrome's on-device AI (the worker never shows Chrome's AI such a box and refuses a guess for one): signatures and initials, texted, emailed or verification codes, security questions, usernames, consent, attestation, agreements, and terms. The SSN box takes the saved SSN only through its own rule, and nothing else. A box under another person's section heading, such as "Student information" or "Child 1", is treated as that person's and gets none of the applicant's details. Never auto-submit an application or guess information. Explicitly document verified mapping coverage versus pending live validation.

## Browser sidebar and conditional fields

Chrome 116+ uses its native `sidePanel` surface for the checklist. Two extension surfaces may send UI messages to the worker:
- **Side panel:** the exact `panel.html` URL with no tab sender. It passes an explicit `tabId`.
- **On-page widget:** the `panel.html?surface=launcher` iframe inside an Iowa tab. The worker always uses the iframe's own `sender.tab.id` and ignores any `tabId` in the message.

Both may poll `ui:pageState`, send `ui:focusField` from a trusted click, and send `ui:autofill`, `ui:stop`, `ui:showApp`, or `ui:openApp` with `confirmed: true` from a trusted click. Only the side panel may send `ui:desktopStatus` and `ui:unlockWithTouchId` (its Unlock when `touchId` is `ready`), and only the widget may send `ui:openPanel`. Content scripts and page `postMessage` calls have no path to the vault. Neither surface ever receives profile values: they get field keys, fixed labels, completion/missing/manual status, counts, and fixed messages.

`ui:autofill` turns **autopilot** on for that tab and runs a step; `ui:stop` turns it off. Autopilot state lives only in worker memory, and a page can never turn it on. Each step reads the page, skips a `url|pageKey` it has already handled in this run, and acts on the adapter's classification:
- `info`: the content script runs `continuePage`, which clicks the page's recorded Continue once.
- Verified home-address confirmation: a no-data desktop authorization and fresh, single-use content snapshot allow the first suggested home address to be selected, then ordinary Save and Continue. No profile values are requested.
- Other `fillable` pages: the worker checks `status`, sends one `getFields` for `profileRequest(pageKey)`, turns those values into page answers with `pageValues`, and fills them in up to four fresh-preview passes. Each key is attempted at most once, and saved answers that are blank are reported as "need you" keys rather than retried. The verified applicant page may continue only after required-answer, unchanged-document, visibility, and fresh desktop-unlocked checks. The DOB-only Tell Us More page always remains manual after filling.
- A page with a `todo`: autopilot waits with that instruction.
- Otherwise unverified manual pages may use generic rule matching while Autofill is on; any filled values still require the native checks, and Next stays manual. Recognized manual/protected Iowa contexts carry instructions that prevent generic fallback.
- When neither verified behavior, a manual instruction, nor generic matches apply, autopilot turns off with "SecondHand doesn't know this page yet."

A step runs when the tab finishes loading and on widget polls. Autopilot turns off after 15 steps, on a locked or unreachable desktop, on a cancelled or failed fill, when the tab closes, or when a page load leaves Iowa's portal. The worker re-reads the tab on every load, because Chrome hides other sites' URLs without the `tabs` permission. Values are released when each fill finishes.

The result is `{ state: 'done' | 'waiting' | 'continuing' | 'stopped' | 'locked' | 'offline' | 'error', filled, needYou, message, todo?, pageKey, held? }`. A general-engine fill (an approved site, or an Iowa page the adapter hasn't verified) adds `left: [{ key, label }]`, the questions left for the applicant with the form's own labels, and `filledQuestions: [{ label, guessed }]` (at most 80), the questions it filled; the side panel lists both by label. It is kept per tab until that tab navigates. `held` (a site's fill only) counts the need-you questions waiting for Fill sensitive details. `ui:pageState` returns `{ page, scan, result, autopilot }`.

Save to My information (#98): after a general-engine fill (an approved site, or an Iowa page the adapter hasn't verified), the worker keeps, per tab and in memory only, the questions the rules matched to a `SAVE_FIELDS` key whose saved value was blank: `{ frameId, planId, token, key, label }`, forgotten when the tab navigates or a new fill replaces them. For the side panel only, `ui:pageState` adds `savable: [{ id, label, answered }]` when there are any; `answered` comes from the content script's `secondhand:generic:answered { token, ids }` reply, which lists which of those plan ids hold an answer and nothing else. `ui:saveAnswer { id, confirmed: true }` is accepted only from the side panel's trusted click. The worker checks the id is kept, the tab's address unchanged, and the site (and that frame) still on, then sends `secondhand:generic:read { token, id, key }`. The engine answers `{ value }` in the profile's format, `{ empty }`, `{ unreadable }` (a typed date is read only in the order its box asks for, or when its numbers allow one order), `{ repeated }` when the page asks for the same field in more than one box (#142), or `{ readable: false }` for a box it may not read (not in its current plan, not the key its rules matched there, a password, code, signature, consent, security-question, username or SSN box, or a box naming another person). The value goes only into `saveFields` and is not kept.

Fill sensitive details (#176): after a fill on an approved site whose `getFields` reply named `held` fields, the worker keeps, per tab and in memory only, the questions of the click's last plan that the rules matched to a key needing one of them (`SecondHandGeneric.requestKeys`, so an age range waits for a held date of birth): `{ frameId, documentId, planId, token, key, label, url, fields }`, with the address of the frame's site and the held fields that question needs. They stay in `needYou`, `result.held` counts them, the summary says how many wait (and a page with nothing else filled says how many need the applicant, not that nothing matched), and they are never `savable`. A reply naming a field the request didn't ask for, one named twice or also answered, an empty or non-list `held`, or any `held` on Iowa's portal is refused as `worker.desktopUnexpected` and fills nothing. They are forgotten when the tab loads a page or closes, the site is turned off or Chrome takes it back, a frame's document moves on (that frame's questions only), or the next Autofill or widget plan replans the page. For the side panel only, `ui:pageState` adds `held: [{ id, label }]` when there are any. `ui:fillHeld { confirmed: true }` is accepted only from the side panel's trusted click. For each site with held questions, in page order, the worker sends `getFields { url, fields, sensitive: true }` with the held fields its questions need; a reply that holds anything back is refused. With the receipt that reply gave, it checks a fresh unlocked status, the tab's address, and fills those questions only, with `secondhand:generic:fill` on the kept plan token (one pass, so the plan and its Save offers stay current). The app answered for that site, so its questions no longer wait, filled or not; one without a saved answer stays under need-you. Cancel ("You cancelled…") is `worker.heldCancelled`: what filled stays, and the site's questions, and any later site's, stay held. The tab's result then counts what filled, drops it from `needYou`, and gives the new `held` count, and the reply is that result. With nothing kept, `ui:fillHeld` is `worker.heldGone`. While its result has `held`, the widget adopts the worker's result at each poll, so its need-you count follows the side panel's fill.


## Home-address confirmation and generic sites

`extension/address-policy.js` loads before the Iowa adapter in content scripts and the worker and is included in prepared extension assets. The observed home-only `addressValidation` page can select the first structurally verified suggestion, then continue. Widget/sidebar and desktop trust copy disclose the preference. This is selection from Iowa’s candidates, not an address-correctness determination or a new profile default. Private single-use snapshots bind the document, URL, control identities, address text, selection, and form state without exposing values to the sidebar. Mailing confirmation, visible county questions, unknown controls, errors, and rendered dialogs pause. See [the address contract](address-automation.md). Public 0.4 downloads predate this integration.

For otherwise unverified Iowa pages, generic rule matching can fill recognized fields but never enables automatic navigation. For other HTTPS sites, optional origin permission and local desktop trust are separate approvals. The generic adapter fills once per explicit click and never navigates or submits. Optional Chrome on-device AI sees unmatched field labels/options and allowed profile-key names, never saved profile values; no cloud AI fallback exists. Embedded forms require their own origin approval. Iowa’s recognized manual or protected steps must not fall through to generic mapping.
