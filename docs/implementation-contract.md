# Internal implementation contract

Runtime: Electron desktop, plain HTML/CSS/JavaScript renderer, Manifest V3 Chrome extension. No application backend or cloud AI. CommonJS desktop modules (`.cjs`); browser scripts are plain JS. Node test runner.

## Desktop renderer API

`window.secondHand` exposes async methods returning plain values or throwing sanitized errors:

- `status()` -> `{ exists, unlocked, lockRevision, recoveryKey, deviceReset, deviceResetSupported, extensionId, autofillWithoutAsking, trustedSites, alwaysAllowedSites, allSites, householdNoteDismissed, touchId, touchIdSupported, touchIdNotice, bridgeRunning, platform, extensionSetup }`; setup contains `{ directory, extensionId, version, build, exists, prepared, newerCopy }`, or `{ prepared: false, available: false }` if bundled assets are unavailable. `newerCopy` is the build of a whole copy a newer app prepared in the folder, which this app never replaces with its own older build (#142), or null. `touchId` is `'ready'` or `'off'`: once on, Touch ID stays ready until it's turned off, with no password-first rule after a restart and no time limit (the owner's choice; see [security](security.md#touch-id-unlock-macos)); `touchIdSupported` is true only on macOS when `canPromptTouchID()` is; `touchIdNotice` says why Touch ID was turned off, or is null; `settingsNotice` says what was reset when `settings.json` couldn't be read at startup, or is null

- `createVault({ password, allowDeviceReset })` -> `{ status, recoveryKey, deviceResetFailed }`; the recovery key is returned once and never stored
- `unlock(password)` -> status
- `resetPassword({ recoveryKey, password } | { method: 'device', password })` -> status (unlocked with the new password; Touch ID stays on, since the data key is unchanged)
- `startOver({ confirmation })` -> status (locked only; `confirmation` must be the typed phrase `start over`). Erases the encrypted file, copies kept by earlier restores, and the reset secret for this computer, and Touch ID's key; Chrome extension settings stay. `status.exists` is then false, so a new password can be created
- `replaceRecoveryKey()` -> `{ recoveryKey }` (unlocked only; retires the previous key)
- `setDeviceReset(enabled)` -> status (unlocked only)
- `setTouchIdUnlock({ enabled: true, password } | { enabled: false })` -> status (unlocked only). Turning Touch ID on checks the password; see [security](security.md#touch-id-unlock-macos)
- `unlockWithTouchId()` -> status (unlocked), or throws why not: Touch ID is off, the prompt was cancelled, or Touch ID was turned off and why
- `saveRecoveryKey(recoveryKey)` -> `{ cancelled }` / `copyRecoveryKey(recoveryKey)` -> true
- `lock()` -> status
- `getData()` -> `{ profile, applications }`
- `saveProfile(profile)` -> saved profile
- `setupProgress()` -> `{ step, steps: 6 }` or `null` (unlocked only). The guided first-run setup's progress: how many of its six steps are done, or `null` when no setup is under way. An unreadable progress file fails with an error.
- `startSetup()` -> `{ step: 0, steps: 6 }` (unlocked only). The renderer calls it right after `createVault`, then offers the setup once the recovery key is saved.
- `saveSetupProgress(step)` -> `{ step, steps: 6 }` or `null` (unlocked only; `step` a whole number 0 to 6). Steps done never go down; 6 finishes the setup and removes its progress file. Refused when no setup is under way. Progress lives in `setup-progress.json` (`{ version: 1, step }`) beside `settings.json`, never in the vault, and a restored backup removes it.
- `onProfileChanged(callback)` -> unsubscribe function; the callback receives `{ fields }`, the names of the saved fields a `saveFields` request changed, never their values
- `onOpenHousehold(callback)` -> unsubscribe function (#180); the callback receives nothing. The extension's `openHousehold` request asks the window to open My information at Your household: at once when unlocked (leaving the guided setup, if it is open, for the whole form), or right after the next unlock when locked.
- `dismissHouseholdNote()` -> status (unlocked only; #180). Overview shows "Add your household: SecondHand can then answer questions like “# of children 0–5”." with **Add your household** and **Dismiss** while no household list is saved. Dismiss saves `householdNoteDismissed: true` in `settings.json` (written only once dismissed), and `status.householdNoteDismissed` keeps the note away from then on.
- `saveApplication(application)` -> saved application (empty/missing id creates UUID)
- `deleteApplication(id)` -> true
- `openPortal()` -> true (fixed Iowa URL only)
- `openExtensionGuide()` -> true (opens SecondHand's fixed `/chrome-extension` guide; in development only, `SECONDHAND_WEBSITE_URL` can point it at a local http(s) website)
- `prepareExtension()` -> `{ directory, extensionId, version, prepared, manifestPath, folderOpened }`; copies bundled assets into the fixed local extension folder and registers its stable ID; never installs into Chrome
- `openExtensionFolder()` / `copyExtensionFolderPath()` -> true (fixed prepared folder only)
- `copyChromeExtensionsUrl()` -> true (copies the fixed `chrome://extensions` address)
- `connectExtension(extensionId)` -> `{ extensionId, manifestPath }` (register native host for current OS)
- `removeTrustedSite(origin)` -> status (unlocked only; removes an exact previously approved origin, and Always allow on it).
- `removeAlwaysAllowedSite(origin)` -> status (unlocked only; takes back Always allow on an exact origin in `alwaysAllowedSites`, which stays trusted). The app can only remove one: only the sensitive dialog adds it.
- `turnOffAllSites()` -> status (unlocked only; clears `allSites`). The app can only turn all websites off: Chrome's prompt comes from the extension.
- `setAutofillTrust(enabled: boolean)` -> status. Stores `autofillWithoutAsking` with `extensionId`, separately approved `trustedSites`, and `alwaysAllowedSites` (saved only while it has any) in the non-sensitive `settings.json`, never in the vault. Requires an unlocked vault. Status carries `alwaysAllowedSites` too.
- `exportBackup()` / `importBackup()` -> `{ cancelled: boolean }` (native dialogs, encrypted vault bytes only; import only while locked, and it turns Touch ID off: the restored file is a different one)
- `onLocked(callback)` -> unsubscribe function; the callback receives `{ lockRevision }` (invalid or legacy notifications provide no revision and still clear sensitive UI)
- `onUnlocked(callback)` -> unsubscribe function; called with `{ lockRevision }` when the side panel's `unlockWithTouchId` unlocked SecondHand, so the window reads status and shows the saved information

`lockRevision` is a monotonic, process-local counter used to correlate a lock response with its notification. The renderer applies a transition once, regardless of their delivery order, so a delayed duplicate notification cannot erase a newly typed passphrase or authentication error. A newer lock transition must still clear sensitive UI and invalidate pending data loads. The counter is not an applicant field or persisted vault data.

Profile contains optional string fields allowlisted by `shared/schema.cjs`, the `householdMembers` list, the bounded local preparation records in `shared/snap-information.js`, and encrypted `customFields` validated by `shared/custom-fields.cjs`. See [SNAP preparation coverage](snap-information.md) for the extra fields and record lists; storing them does not add portal mappings. Core fields include:

- Identity: firstName, middleName, lastName, suffix, maidenName, isApplicant, birthDate (YYYY-MM-DD), ssn.
- Contact: email, phone (reference only, not automatically assigned a type), homePhone, mobilePhone, bestContactTime (at most 30 characters).
- Home: hasHomeAddress, addressLine1, addressLine2, city, state, zip, county.
- Mailing: mailingSameAsHome, mailingAddressLine1, mailingAddressLine2, mailingCity, mailingState, mailingZip.
- Explicit requests: programSnap, programFip (FIP or RCA), programMedicaid, helpPayMedicalBills (the portal asks about the last three calendar months).
- Household and preparation notes: householdSize, monthlyEarnedIncome, monthlyOtherIncome, monthlyRent, monthlyUtilities, householdAdults, householdChildren, householdSeniors, householdVeteran, householdDisability, assetsOnHand, monthlyMedicalExpenses, householdAllCitizens, householdLegalStatus, householdPregnant, householdMedicare.
- The applicant's own answers to Iowa's Tell Us More questions: sex, maritalStatus, hasSsnAnswer, ssnCardNameMatches, usCitizen, militaryOrVeteran, disabled, blind, healthLimitation, medicare.
- Answers pantry intake forms ask for (#184): studentLevel (blank, `not-student`, `high-school`, `undergraduate`, `graduate`, or `other`), and three answers chosen from lists (`SEVERAL_CHOICES`), each saved as its chosen codes, comma-separated in the list's order: incomeSources (`job`, `self-employment`, `financial-aid`, `family-support`, `unemployment`, `social-security`, `child-support`, `pension`, `other`, `none`), currentBenefits (`snap`, `wic`, `cash-assistance`, `medicaid`, `ssi`, `housing`, `school-meals`, `none`) and helpWanted (`food-pantry`, `fresh-produce`, `food-vouchers`, `gift-cards`, `snap-help`, `social-services`, `other`). An unknown code, a code chosen twice, or `none` with anything else is refused. incomeSources and currentBenefits are in `SENSITIVE_FIELDS`.
- The household list (#98): `householdMembers`, an array of up to 20 `{ id, firstName, lastName, birthDate, relationship, student, grade }`. `id` is a UUID, unique in the list. Names are trimmed, at most 100 characters; `birthDate` is blank or a real YYYY-MM-DD date; `relationship` is blank or one of `self`, `spouse-partner`, `child`, `parent`, `sibling`, `grandchild`, `other-relative`, `other`; `student` is blank, `yes`, or `no`; `grade` is at most 20 characters and only for a student. Every person but the applicant needs a first name. A nonempty list has exactly one `self` row, which always takes the applicant's own `firstName`, `lastName`, and `birthDate`, and, once `studentLevel` is answered, `student` from it: `no` for `not-student`, `yes` for any level. Without a `studentLevel`, the row keeps a `student` answer saved before #184. Profiles without the list read it as `[]`.

Birth dates (#135): a save (`saveProfile`, `saveFields`) refuses the applicant's or anyone's birth date that is after today or more than 130 years ago, naming whose it is ("Your" or "Person 3’s", as My information numbers its rows). Today is this computer's own date, in its own timezone, never the UTC date (`shared/household.cjs` `localDate`). A profile read back from the vault (`validateStoredProfile`) does not check birth dates against today, so a clock set back, or a date saved before the 130-year limit, never keeps the information from opening. Such a stored date is never filled into a page and gives no age: answers worked out from it stay with the applicant, and the reply says why (`reason`, below). While one is saved, `saveFields` is refused with whose date it is and to fix it in My information. The Iowa adapter fills a date of birth only under the same rule, on the same local date. Development tests may pin today with `SECONDHAND_TEST_TODAY` (YYYY-MM-DD), which needs `SECONDHAND_TEST_MODE=1` and is refused by a packaged app.

`hasHomeAddress`, `mailingSameAsHome`, `isApplicant`, the four request fields, and the household Yes/No fields listed in `YES_NO_FIELDS` accept only `''`, `'yes'`, or `'no'`. An explicit `'no'` is a real answer and is released when approved; `''` is unknown and omitted from field responses. Programs are independent user choices, not eligibility determinations. `suffix` accepts blank, I through X, Jr., or Sr. `sex` accepts blank, Male, or Female, and `maritalStatus` blank or one of Iowa's choices: Divorced, Legally Separated, Married (includes common-law), Never Married, Separated, Widowed. A saved `ssn` with `hasSsnAnswer` `'no'` is rejected. All other values remain bounded strings. No field defaults, boolean coercion, inferred programs, copied mailing addresses, or inferred address answers are permitted. Old encrypted profiles normalize absent new keys to blank in memory; opening them does not rewrite the vault. The profile payload remains version 1. New encrypted vaults use the version 2 envelope with password/recovery key slots; legacy version 1 envelopes remain readable.

While `householdMembers` has people, `householdSize`, `householdAdults` (18–64), `householdChildren` (under 18) and `householdSeniors` (65+) are worked out from it, ages as of today, and win over the saved manual counts; an age count needs every person's birth date, usable on today, and is otherwise blank. My information shows those counts read-only, and names whose birth date keeps them blank. `shared/schema.cjs` `releasedValue(profile, field)` is the one place a released answer is worked out: saved fields as saved, `hasSsn`, `studentNameGrade` (the one student's "First Last, Grade", only when exactly one person is a student, every other person's answer is No, and the grade is saved), the list's counts, and age-band counts `householdCount:L-H` or `householdCount:N+` (whole numbers 0 to 120 without leading zeros, L ≤ H), counted from birth dates only. `householdMembers` itself is never released.

Saved profile fields are broader than live autofill coverage. The Iowa adapter requests only its verified page-scoped keys: 25 initial applicant keys, birthDate on the separately scoped primary-applicant Tell Us More page, and on the fully captured `dynamicQuestionsStart` and legacy `dynamicQuestions` layouts the applicant's own Tell Us More answers plus the household citizenship, disability and Medicare answers that can settle a question the applicant left blank. `hasSsn` is worked out by the desktop (Yes when an SSN is saved, else the saved `hasSsnAnswer`) and never carries the number. The captured full layouts also map the visible SSN and separate saved Social Security card names in their exact conditional controls. The hidden submitted SSN mirror is never written. That complete layout may continue only when every visible question has supported controls and an answer, any submitted SSN matches the visible number, and no errors, dialogs, or unknown controls remain. The partial birth-date-only layout always needs manual Next. Email, county, other household notes, and financial record lists do not acquire verified mappings from their presence in the profile. The generic engine may map some scalar fields on other pages, subject to its own rules and native approval; this does not establish Iowa-specific coverage. The six captured later scalar layouts use page-scoped requests. The five financial record scopes below use a separate one-record protocol; all other record layouts and Add Another remain manual. The schema-valid `tests/fixtures/applicant-profile.json` is entirely fictional; automated tests keep it isolated. A separately authorized manual live inspection is recorded in `docs/iowa-live-journey.md` and stopped before signing or submitting.

`customFields` is an optional list of at most 50 `{ id, label, value, aliases, type?, options?, site? }` records. IDs are unique UUIDs; labels and up to five distinct aliases are bounded to 120 characters, values to 1,000. Old profiles normalize an absent list to `[]`. An answer saved from a page with Remember for next time (#186) also has `type` (`text`, `textarea`, `number`, `date`, `email`, `tel`, `radio` or `select`), `options` (its choices, at most 30 of up to 120 characters, none twice by their words; empty for a text box) and `site` (the https origin it came from); its value must fit its type and, for a choice, be one of its options. `type` and `options` go together; `site` is kept when known. Records without them load and match as before. The whole list stays inside the desktop vault; it is excluded from scalar field release and model prompts. Exact-label matching normalizes Unicode compatibility, case, whitespace, and trailing colon/asterisk markers. Multiple saved matches or duplicate requested labels are refused; there is no fuzzy/model match. Custom choice answers must equal one listed option, and all answers must fit the requested control type. A record with `type` matches only a question with the same type, the same set of choices, and the same words (`questionWords` in `shared/custom-fields.cjs`: lowercase, accents and punctuation removed, a leading question number and a trailing "required" or "optional" dropped, words in every script kept), by its label or an alias; a choice is answered with the page's own option of the same words, and such a record that two questions would take answers neither.

Applications: `{ id, program: 'Iowa SNAP', status, createdAt, updatedAt, confirmationNumber, notes, nextAction, dueDate }`. Allowed status: draft, in_progress, submitted, needs_action, approved, denied. Submitted requires confirmationNumber. Manual user records clearly labeled. No invented deadlines.

## Native bridge protocol (extension ↔ host)

Host name `org.secondhand.bridge`. Each request `{ id: string, type, ...payload }`. Response `{ id, ok: true, data }` or `{ id, ok: false, error: string, code? }`. The only codes are `LAYA_NOT_READY` and `DESKTOP_UNREACHABLE`. The macOS/Linux host answers `DESKTOP_UNREACHABLE` when it can't reach the running desktop app; the Windows relay and older hosts send the same failure without the code, and the extension treats both as the app being closed.

- `status` -> `{ unlocked, applicationCount, accessRevision, allSites, customFieldsAvailable?, laya: { state }, extension, touchId }` (no profile values). When `allSites` isn't `true`, the extension turns all websites off in Chrome. `state` is `off`, `unavailable`, `not-downloaded`, `downloading`, `ready`, or `error`. `touchId` is `ready` or `off`.
- `unlockWithTouchId` -> `{ unlocked: true }` or `{ unlocked: false, reason: 'off' | 'cancelled' }` (#99). Carries only `id` and `type`. When SecondHand is locked and Touch ID is ready, the app shows macOS's Touch ID prompt and unlocks as a password unlock does. Nothing else about Touch ID, and never a password, passes through Chrome.
- `showApp` -> `{ shown: true }`. Shows and focuses the desktop window so the user can unlock. Works while locked and returns no profile data.
- `openHousehold` -> `{ shown: true }` (#180, the side panel's **Add your household**). Carries only `id` and `type`. Shows and focuses the desktop window and tells it to open My information at Your household (`secondhand:open-household`, which carries nothing); while locked, the window opens there once unlocked. Works while locked, reads nothing, and returns no profile data. The native hosts relay it like any request: with the app closed it fails as unreachable, and it never starts the app.
- `openApp` -> `{ opened: 'shown' | 'launched' }`. Carries only `id` and `type`. The macOS/Linux native host handles it itself: it relays `showApp`, and a running app comes forward (`shown`). If the app can't be reached, the host starts SecondHand (`launched`): its own executable, detached with no output, with no arguments when packaged and with the app path in development, never with Chrome's origin or anything from the request. It keeps `SECONDHAND_USER_DATA` and drops test-only settings. One start per host process; a failed start answers `SecondHand could not be started (CODE).` The Windows relay passes `openApp` on unchanged to a running app, which answers `shown`. If the app can't be reached (no bridge session, an unreadable one, or no app answering on its pipe), the relay starts `secondHand.exe` from its own folder (`launched`): no arguments, none of the relay's handles, the relay's environment less the test-only settings, and nothing from the request. It too starts the app at most once per relay process, and a failed start answers `SecondHand could not be started (Windows error N).` Chrome starts a host for each request, so two quick clicks can start the app twice; the desktop's single-instance lock keeps one running.
- `getFields` `{ url, fields: string[], sensitive?: true }` -> `{ values: { field: value }, accessRevision, held?: string[], reason?, household? }`. `reason: 'birthDate'` when a requested answer was left out because a saved birth date it needs is after today or more than 130 years ago; the side panel says so with the fill's result. `household` (#180, sites other than Iowa's portal only) says what the household list lacks for the household questions the request left unanswered (`shared/household.cjs` `listNeed`): `{ need: 'list' }` when no list is saved and an age-band key, `householdSize`, `householdAdults`, `householdChildren`, `householdSeniors` or `studentNameGrade` got no answer; `{ need: 'birthDate', person }` when a list is saved, an age-band key or `householdAdults`, `householdChildren` or `householdSeniors` got no answer, and a member has no birth date, `person` naming the first such member as My information does (`'you'` for the applicant's own row, otherwise their row number, 1 to 20), never by name. It is absent otherwise. Requires an unlocked vault and the approved extension ID. Fields are the schema's request fields (all record lists and `householdMembers` excluded, `hasSsn` and `studentNameGrade` included) and up to 20 age-band keys (`householdCount:0-5`, `householdCount:60+`), each answered as `releasedValue` works it out. Iowa requests use the exact HTTPS origin and portal path. Other HTTPS sites additionally require an explicitly trusted origin, or `allSites` on. Fields are strictly allowlisted, and only requested nonblank values are returned.
  - When `autofillWithoutAsking` is on and the caller's extension ID matches the stored one, eligible requests return without a dialog, sensitive fields included (#175). So do requests from a site in `alwaysAllowedSites`, for that extension ID; Iowa's portal never follows that list.
  - Otherwise a desktop dialog names the fields, with the buttons **Cancel**, **Allow once**, and **Always allow on this computer**. "Always allow" turns the setting on and saves it.
  - The dialog rechecks the unlocked vault, the access revision, and the extension ID before releasing values, so a lock and re-unlock while it is open invalidates the answer.
  - Registering a different extension ID turns the setting off and empties `alwaysAllowedSites`.
  - Other sites require desktop `trustSite` approval and Chrome’s optional origin permission. On those sites, when the request would need a dialog, Autofill's request holds its `SENSITIVE_FIELDS` fields back (#176): the dialog above names only the others (and none shows when every field asked for is sensitive), the reply carries only their values, and `held` names the sensitive fields in request order. Nothing is read for a held field, and `reason` speaks only for the fields released. `held` is absent when nothing was held back: always on Iowa's portal, and whenever Always allow (on this computer or on this site) covers the request.
  - `sensitive: true` is the side panel's **Fill sensitive details** (#176). It asks for held fields alone: every field must be in `SENSITIVE_FIELDS`, and the URL may not be Iowa's portal (the bridge refuses `sensitive` with any other value, on Iowa's portal, or as an empty navigation request; the desktop refuses an everyday field with "Only sensitive details on a site other than Iowa’s application are asked for this way."). Nothing is held back from it. Unless Always allow covers the site, it gets the "Share sensitive details?" dialog for those fields alone, with **Cancel** (the default), **Allow once**, and **Always allow on this site**, and Cancel refuses it with "You cancelled this field request." Always allow on this site adds the origin to `alwaysAllowedSites` (at most 50; the 51st is refused with the reason) and saves it, moving `accessRevision` on. Household counts are not sensitive: age-band keys, and `householdAdults`, `householdChildren` and `householdSeniors`, those worked out from the household list included.
  - `alwaysAllowedSites` loses a site on `untrustSite` or `removeTrustedSite` for it, loses every site not in `trustedSites` when all websites turns off, and empties when a different extension ID is registered. At startup it keeps only https origins SecondHand is on, and only with a valid saved extension ID.
  - An empty `fields: []` is accepted only for the exact Iowa `enterPersonalInfo`, `addressValidation`, `dynamicQuestions`, `dynamicQuestionsStart`, or `ssaVerificationRender` URL, with no query, fragment, or trailing slash. It authorizes a disclosed continuation or first-home-suggestion action under the same unlocked/trust checks and returns `{ values: {}, accessRevision }` without reading the saved profile. These URLs grant no page coverage by themselves: the content adapter still requires the exact supported applicant context, known answered controls, and ordinary Next snapshot before clicking.
- `getCustomFields` `{ url, fields: [{ id, label, type, options }], sensitive?: true }` -> `{ values: { questionId: value }, accessRevision, held?: string[] }`. General trusted HTTPS origins only; Iowa is excluded. Up to 40 questions, labels/options at most 120 characters, at most 30 options, 48 KiB bounded requests/releases. Only uniquely matched explicit custom answers are released. Credentials, banking/payment details, legal confirmations, and other-person questions are excluded. Released answers follow `getFields`' approval rules (#186): an everyday one gets the ordinary dialog ("Fill these custom answers into …?", naming each question and answer) unless Always allow covers it, and its cancel returns no values. An answer to a question about a sensitive subject (`sensitiveCustomQuestion`, by the question's label and options) is held back unless Always allow, on this computer or on this site, covers the request: nothing of it is shown, and `held` names its question ids. `sensitive: true` (Fill sensitive details) asks for held questions alone: every question must be about a sensitive subject (otherwise "Only sensitive details on a site other than Iowa’s application are asked for this way."), nothing is held back, the "Share sensitive details?" dialog names each question and answer with **Cancel**, **Allow once** and **Always allow on this site**, and Cancel refuses it with "You cancelled this field request." No saved catalog, model context, file path, or arbitrary key projection is returned. `status.customFieldsAvailable` signals only that a nonempty list exists while unlocked.
- `rememberAnswers` `{ url, answers: [{ label, type, options, answer }] }` -> `{ remembered: number }` (#186, Remember for next time). General trusted HTTPS origins only; Iowa is excluded. One to 20 answers, each with exactly those keys: a label of at most 120 characters with words to match, a type `rememberedAnswer` takes (`text`, `textarea`, `number`, `date`, `email`, `tel`, `radio`, `select`), options as `customFields` keeps them, and an answer of at most 1,000 characters that fits its type (a line break only in a `textarea`), one of the options for a choice, all by the page-text rule. Requires an unlocked vault. A question only the applicant answers, payment details, another person's details, a question asked twice in one request, one a custom answer typed in My information already covers ("You already have a custom answer for “…”. Change it in My information."), and a list that would pass 50 ("You have 50 custom answers, the most SecondHand keeps. Remove one in My information, then remember this answer again.") are refused before any dialog. One confirmation, "Remember this answer?" or "Remember these answers?" ("Remember sensitive details?", the warning form with Cancel by default, when one is about a sensitive subject), names each question and answer, with **Cancel** and **Remember**; Cancel refuses it with "You cancelled. Nothing was remembered." It shares the one-approval-at-a-time guard and rechecks the unlocked vault, the access revision, the extension ID and the site after the dialog. It adds each answer as a custom answer with its `type`, `options` and `site`; one already saved from a page for the same question takes the new answer and keeps its first site. Only `customFields` changes; the save moves `accessRevision` on and sends the renderer `secondhand:profile-changed { fields: ['customFields'] }`.
- `authorizeSiteNavigation` `{ url }` -> `{ accessRevision }`. General trusted HTTPS origins only; no profile fields are read or returned. The existing approval/Always allow gate discloses ordinary Next/Continue/Save and Continue and that the site may save entered answers. The extension must retain the pre-approval navigation token and recheck its active tab, origin, unlocked receipt revision, and unchanged document immediately before clicking. This authorization never covers consent, certification, signature, payment, or final submission.
- `getRecordFields` `{ url, pageKey, recordType, fields, personName? }` -> `{ recordId, values, accessRevision }`, or `{ values: {}, reason: 'recordMissing', accessRevision }`. `desktop/record-fields.cjs` is the fixed registry shared by relay and desktop. Only exact `dynamicQuestions` scopes for jobs, Private Pension/Social Security, rent responsibility, personal utilities, and Cash/Uncashed Check are allowed. `person` is always requested. Names match by trim/case/whitespace only, and only records with explicit owners are candidates. Multiple records require a desktop chooser even under Always allow. Normal approval and the same unlocked/extension/access-revision checks apply; the selected UUID is re-fetched after approval. Only requested validated nonblank strings are projected, with no entire list, model facts, historical tax values, household-total substitution, or default zero. Page context, unique owner option, stale snapshot, and one-use Next guards remain mandatory in the extension.
- `saveFields` `{ url, fields: { key: value } }` -> `{ saved: string[] }` (#98, Save to My information). The URL rules mirror `getFields`: any HTTPS site at the bridge, then a trusted origin, `allSites`, or Iowa's portal at the desktop. Keys come from `SAVE_FIELDS` (the general engine's `PROFILE_KEYS` less `ssn`); each value is a nonblank string of at most 200 characters that passes the page-text rule, and the merged profile must pass `validateProfile`. The page-text rule (`UNSEEN` in `desktop/bridge.cjs`) refuses text with a character that reorders, hides, or breaks the words around it: a control character (C0, DEL, C1), a format character (bidi controls such as U+202E, zero-width characters, tag characters), a line or paragraph separator (U+2028, U+2029), or another default-ignorable character (variation selectors, the soft hyphen, fillers). U+200C ZERO WIDTH NON-JOINER and U+200D ZERO WIDTH JOINER are allowed, because Persian, Arabic, and Indic words need them. Such text is refused, never stripped, so a desktop dialog shows only the page's own text. Requires an unlocked vault. Only blank fields are saved: an answer already saved, or a household count while the household list sets it, is refused with the reason. One desktop confirmation, "Save to My information?", names each field and value with **Cancel** and **Save** (the warning form, Cancel by default, for sensitive fields); there is no Always allow. It shares the one-approval-at-a-time guard and rechecks the unlocked vault, the access revision, and the extension ID after the dialog. A save moves `accessRevision` on and sends the renderer the changed field names. The extension sends it only from a trusted side-panel click, after reading that one box (see below).
- `trustSite` `{ url }` -> `{ trusted: true, origin }`; a native desktop prompt approves a non-Iowa HTTPS origin before adding it to the local trusted-site list.
- `untrustSite` `{ url }` -> `{ trusted: false, origin }`. Removes an HTTPS origin from the trusted-site list, and from `alwaysAllowedSites`, when the extension turns that site (or an embedded form) off; needs no unlock or prompt.
- `trustAllSites` -> `{ allSites: true }`. Carries only `id` and `type`. Requires an unlocked vault; one desktop prompt approves every HTTPS site and saves `allSites` in `settings.json`. Sensitive fields follow `getFields`' other-site rule on each site.
- `untrustAllSites` -> `{ allSites: false }`. Carries only `id` and `type`. Clears `allSites`, and drops from `alwaysAllowedSites` every site not in `trustedSites`; needs no unlock or prompt.
- `recordProgress` `{ url, filledCount: integer }` -> `{ recorded: true }`. Updates a draft/in_progress Iowa application, no page HTML, no profile values, no inferred submitted/approved status. Requires unlocked vault.
- `warmLaya` -> `{ state }` (#39, #42). When an Autofill click starts on a page with questions Laya may see, the desktop loads Laya's model (its first load after idle takes seconds) before the click's Laya budget starts, then answers with Laya's state. A model that fails to load answers `error`. Reads no saved answers and needs no unlock.
- `suggestFields` `{ url, fields: [{ id, label, type, options }], budgetMs }` -> `{ suggestions: { [id]: key } }` (#39). Laya matches text boxes to saved fields. Up to 40 fields of type `text`, `textarea`, `number`, `date`, `email`, or `tel`; labels up to 200 characters; up to 30 options of up to 100 characters. Labels and options pass the page-text rule (see `saveFields`). The extension (`layaQuestion` in `extension/generic-adapter.js`) leaves a question that breaks it to the applicant and never sends it, so one such question can't make the bridge refuse the rest. Questions carry labels and options only, never saved answers. Keys are never SSN or another saved answer AI may not guess. It returns keys only and needs no approval: their values come through `getFields`, which asks.
- `answerFields` `{ url, questions: [{ id, label, type, options }], budgetMs }` -> `{ answers: { [id]: optionText }, accessRevision, reason? }` (#42). `reason: 'birthDate'`, as for `getFields`, when a question was left unanswered and the facts sheet had no age from a saved birth date it can't use. Laya answers `radio`, `select`, and `checkbox` questions from a facts sheet built from the saved profile inside the desktop app; the sheet never leaves it. Up to 30 questions, same label and option limits.
  - Laya isn't asked for best guesses (#185): they were mostly wrong on the final holdout (#189), so the reply has sure answers only. A 0.5.0 desktop also returns `guesses: { [id]: optionText }` off Iowa's portal, and the extension still reads them: it refuses a reply whose guesses name a question it didn't send, a `checkbox` question, an option the question lacks, a question also in `answers`, or any guess on Iowa's portal. It fills a guess with the engine's `laya-guess` mark, counts it in the result as `layaGuessed`, and lists `layaGuesses: [{ id, label }]` for the side panel. A reply without `guesses` has none.
  - Answers are profile information, so they follow `getFields`' approval: with Always allow on (or the site in `alwaysAllowedSites`) and the stored extension ID, they are returned with no dialog, those that needed a sensitive fact included. Otherwise one dialog lists each question with the option that would be filled, with Cancel, Allow once, and Always allow. When an answer needed a sensitive fact, that same single dialog is the "Share sensitive details?" one with Cancel, Allow once, and Always allow on this site. Cancel there drops only the answers that needed a sensitive fact, and a second "Let Chrome fill this form?" dialog lists only the others. Cancel on that dialog, or on a dialog with no sensitive answers, returns no answers, and a lock or access change while a dialog is open returns none. Iowa's portal follows `getFields`' Iowa rule, with no sensitive dialog. The dialogs share `getFields`' one-approval-at-a-time guard.
  - Both need Laya ready (otherwise they fail with `code: 'LAYA_NOT_READY'` and the extension fills as it does without Laya), a trusted HTTPS site or Iowa's portal, and an unlocked vault. Questions only the applicant answers are never scored: signatures and initials, texted, emailed or verification codes, security questions, usernames, consent, attestation, agreements, terms, and SSN (`UNSAFE_QUESTION`, identical in `extension/generic-adapter.js` and `shared/laya-prompts.cjs`). The confidence bars (0.9 to answer, 0.95 to match, and a clear lead over the runner-up) are in `desktop/laya-decisions.cjs`.
  - Each Autofill click gives Laya 3 seconds in all. The extension asks `suggestFields` first, then `answerFields` with what is left (#90): a text box's candidates are short saved-field descriptions, while each of a choice question's carries the facts sheet, so text boxes take a fraction of the time and a long checklist can't starve them. It sends what the click has left as `budgetMs`, a whole number from 1 to 3000; only time spent waiting on Laya counts, never the applicant's time in an approval dialog. The desktop decides question by question until that deadline and drops any decision made after it; what is left goes to "need you". With a `noul-v1` model it answers the choice questions with the fewest options first, in groups by batches through the model, each group through both of its passes, so long checklists come last.
  - Answers come before `getFields`. An Always allow in `getFields`' dialog outdates their access receipt, so the extension fills none of them and asks for another click; an answer set with nothing to fill is ignored.

Iowa portal URL: `https://hhsservices.iowa.gov/apspssp/ssp.portal`. Exact origin `https://hhsservices.iowa.gov`; path must be `/apspssp/ssp.portal` or descendants, no username/password/other ports.

`accessRevision` is a randomly seeded, process-local safe-integer disclosure revision, separate from the renderer’s `lockRevision`. A fill/Next rechecks that the desktop is unlocked and the revision still matches its field authorization before acting. Lock, profile changes, or connection/trust changes invalidate prior authorization.

The bridge supplies the desktop handler with `{ extensionId }` from the authenticated native envelope; request payloads cannot override this context. The desktop cannot attest Chrome tab IDs, so the extension binds every autofill to the tab that asked for it and re-checks that tab's URL before each fill pass.

Native host relays to running desktop over authenticated local IPC, not HTTP. Desktop is sole vault owner. The extension fills approved mapped fields. Iowa autopilot can continue verified information screens, the complete initial applicant page, the verified first-home-address confirmation, and fully recognized, complete Tell Us More layouts, and the six captured screening/five financial record scopes in [portal coverage](iowa-portal.md); other Iowa navigation stays manual. General-site continuation has the separate optional contract below. It never signs or submits an application. Unknown sections, unanswered questions, signatures, consent, review, passwords, CAPTCHA, MFA, and file inputs stay manual. On other pages the general engine never guesses or fills a box only the applicant answers, whether from its rules, Laya, or Chrome's on-device AI (the worker never shows Chrome's AI such a box and refuses a guess for one): signatures and initials, texted, emailed or verification codes, security questions, usernames, consent, attestation, agreements, and terms. The SSN box takes the saved SSN only through its own rule, and nothing else. A box under another person's section heading, such as "Student information" or "Child 1", is treated as that person's and gets none of the applicant's details. Never auto-submit an application or infer missing Iowa answers or financial record values. Experimental other-site guesses follow the separate restrictions above. Explicitly document verified mapping coverage versus pending live validation.

## Browser sidebar and conditional fields

Chrome 116+ uses its native `sidePanel` surface for the checklist. Two extension surfaces may send UI messages to the worker:
- **Side panel:** the exact `panel.html` URL with no tab sender. It passes an explicit `tabId`.
- **On-page widget:** the `panel.html?surface=launcher` iframe inside an Iowa tab. The worker always uses the iframe's own `sender.tab.id` and ignores any `tabId` in the message.

Both may poll `ui:pageState`, send `ui:focusField` from a trusted click, and send `ui:autofill`, `ui:stop`, `ui:showApp`, or `ui:openApp` with `confirmed: true` from a trusted click. Only the side panel may send `ui:desktopStatus`, `ui:unlockWithTouchId` (its Unlock when `touchId` is `ready`), and `ui:openHousehold` (its **Add your household**, #180), and only the widget may send `ui:openPanel`. Content scripts and page `postMessage` calls have no path to the vault. Neither surface ever receives profile values: they get field keys, fixed labels, completion/missing/manual status, counts, and fixed messages.

`ui:autofill` turns **autopilot** on for that tab and runs a step; `ui:stop` turns it off. Autopilot state lives only in worker memory, and a page can never turn it on. Each step reads the page and uses a nonpersonal semantic step identity. The two Tell Us More routes share one identity, so a reload or alternate route cannot repeat a possibly accepted Next. Each automatic navigation attempt is recorded before sending the click, including an uncertain response; restarting Autofill explicitly starts a new run. A private per-document UUID and single-use snapshot prevent pending requests from acting on a replacement document. The worker acts on the adapter's classification:
- `info`: the content script runs `continuePage`, which clicks the page's recorded Continue once.
- Verified home-address confirmation: a no-data desktop authorization and fresh, single-use content snapshot allow the first suggested home address to be selected, then ordinary Save and Continue. No profile values are requested.
- Captured financial record pages: the worker sends `getRecordFields` for the fixed page/type projection, binds the selected owner and record receipt to fresh private controls, fills only that record in at most six passes, and rechecks access/document state before its ordinary one-use Next. Missing records or conflicts pause; no list, Add Another, or model-derived answer is authorized.
- Other `fillable` pages: the worker checks `status`, sends one `getFields` for `profileRequest(pageKey)`, turns those values into page answers with `pageValues`, and fills them in up to four fresh-preview passes. Each key is attempted at most once, and saved answers that are blank are reported as "need you" keys rather than retried. The verified applicant page may continue only after required-answer, unchanged-document, visibility, and fresh desktop-unlocked checks. A captured complete Tell Us More page also needs every visible question supported and answered (the exact optional card middle name may be blank), a matching submitted SSN when present, its exact ordinary Next control, and no errors or dialogs. The DOB-only Tell Us More page always remains manual after filling. The six exact later scalar layouts may continue only when their complete captured question set is answered, unknown follow-ups and errors are absent, and the exact ordinary Next snapshot remains current.
- A page with a `todo`: autopilot waits with that instruction.
- Otherwise unverified manual pages may use generic rule matching while Autofill is on; any filled values still require the native checks, and Next stays manual. Recognized manual/protected Iowa contexts carry instructions that prevent generic fallback.
- When neither verified behavior, a manual instruction, nor generic matches apply, autopilot turns off with "SecondHand doesn't know this page yet."

A step runs when the tab finishes loading and on widget polls. Autopilot turns off after 64 steps, on a locked or unreachable desktop, on a cancelled or failed fill, when the tab closes, or when a page load leaves Iowa's portal. The worker re-reads the tab on every load, because Chrome hides other sites' URLs without the `tabs` permission. Values are released when each fill finishes.

The result is `{ state: 'done' | 'waiting' | 'continuing' | 'stopped' | 'locked' | 'offline' | 'error', filled, needYou, message, todo?, pageKey, held?, custom?, household? }`. It is kept per tab until that tab navigates. `held` (a site's fill only) counts the need-you questions waiting for Fill sensitive details. `custom` (a site's fill only, #186) counts the answers that came from custom answers, and the summary says "N from your custom answers". `household` (a site's fill only, #180) is `{ need: 'list' }` or `{ need: 'birthDate', person }`, as the first such question's site said it, with `questions: [{ id, label }]`: the need-you questions of the click's last plan the rules matched to a household key (any of them for `list`; only the counts by age for `birthDate`) that got no answer and weren't answered in part. A `getFields` reply's `household` with any other shape, on Iowa's portal, or for a request that left no such question unanswered is refused as `worker.desktopUnexpected` and fills nothing. Fill sensitive details keeps it in the tab's result. `ui:pageState` returns `{ page, scan, result, autopilot }`.

Save to My information (#98): after a general-engine fill (an approved site, or an Iowa page the adapter hasn't verified), the worker keeps, per tab and in memory only, the questions the rules matched to a `SAVE_FIELDS` key whose saved value was blank: `{ frameId, planId, token, key, label }`, forgotten when the tab navigates or a new fill replaces them. For the side panel only, `ui:pageState` adds `savable: [{ id, label, answered }]` when there are any; `answered` comes from the content script's `secondhand:generic:answered { token, ids }` reply, which lists which of those plan ids hold an answer and nothing else. `ui:saveAnswer { id, confirmed: true }` is accepted only from the side panel's trusted click. The worker checks the id is kept, the tab's address unchanged, and the site (and that frame) still on, then sends `secondhand:generic:read { token, id, key }`. The engine answers `{ value }` in the profile's format, `{ empty }`, `{ unreadable }` (a typed date is read only in the order its box asks for, or when its numbers allow one order), `{ repeated }` when the page asks for the same field in more than one box (#142), or `{ readable: false }` for a box it may not read (not in its current plan, not the key its rules matched there, a password, code, signature, consent, security-question, username or SSN box, or a box naming another person). The value goes only into `saveFields` and is not kept.

Add your household (#180): the side panel lists a result's `household.questions` by their own words under **Household questions**, says what the list lacks (no list saved, "Your date of birth is missing…", or "Person N on your household list has no date of birth…"), and offers one button: **Add your household**, or with a list saved, **Open your household list**. Its trusted click sends `ui:openHousehold { confirmed: true }`, which the worker sends on as `openHousehold` with nothing beside its id and type; any reply but `{ shown: true }` is `worker.desktopUnexpected`. The questions stay listed until the next Autofill. The widget adds "N household questions wait in the side panel" to its line.

Remember for next time (#186): after a fill on an approved site (never on Iowa's portal), the worker keeps, per tab and in memory only, the open questions of the click's last plan that `SecondHandGeneric.canRemember` takes (a question `canCustom` takes, of type `text`, `textarea`, `number`, `date`, `email`, `tel`, `radio` or `select`, with a label of at most 120 characters, never a search box), except one whose custom answer the app held back: `{ frameId, documentId, planId, token, label, url, question: { label, type, options }, timeBound }`, where `timeBound` (`SecondHandGeneric.timeBound`) says the answer changes over time (a date box, or words about dates, times, days, pickups, appointments, deliveries, visits, this week or month). They are forgotten when the tab loads a page or closes, the site is turned off or Chrome takes it back, or a frame's document moves on, and the next fill replaces them. For the side panel only, `ui:pageState` adds `rememberable: [{ id, label, timeBound, answered }]` when there are any, `answered` from `secondhand:generic:answered`. The side panel shows each answered one with a checkbox, checked unless `timeBound`, and keeps the applicant's choices across polls. `ui:rememberAnswers { ids, confirmed: true }` (1 to 20 kept ids, each once) is accepted only from the side panel's trusted click. The worker checks the ids are kept and the tab's address unchanged, then sends `secondhand:generic:readOpen { token, id }` for each, in the document Chrome placed. The engine answers `{ value }` (a box's words, or the chosen option's own text, at most 1,000 characters, with a line break only in a text area), `{ empty }`, `{ unreadable }`, `{ repeated }` when the page asks the same question in more than one box, or `{ readable: false }` for a box it may not read (not in its current plan, matched by a rule, or one `canRemember` refuses). Those are `worker.rememberEmpty`, `worker.rememberUnreadable`, `worker.rememberRepeated` and `worker.answerGone`, and nothing is sent. Then, for each site, `rememberAnswers` in that site's own name; "You cancelled…" is `worker.rememberCancelled`, any other refusal is shown in the app's words, and the questions stay listed. Remembered questions leave the list. The values go only into `rememberAnswers` and are not kept.

Custom answers held for Fill sensitive details (#186): a `getCustomFields` reply's `held` must name questions the request asked, each once, none also answered, and never be empty; anything else is `worker.desktopUnexpected` and fills nothing. A held question isn't asked about again in that click, and neither Laya nor Chrome's AI guesses it. It counts under `needYou` and in `result.held`, and joins the held list as `{ frameId, documentId, planId, token, label, url, question }`. Fill sensitive details sends, for each site, `getFields { …, sensitive: true }` for its held saved fields as before, then `getCustomFields { url, fields, sensitive: true }` for each frame's held custom questions; every reply's receipt must agree. What they release fills those questions only, and the result's `custom` counts the custom answers placed.

Answers from lists (#184): the rules match student status, income source, current benefits and help-wanted questions, and a yes or no about the household getting one benefit (`receivesSnap`, `receivesWic`, `receivesCashAssistance`, `receivesMedicaid`, `receivesSsi`, `receivesHousingAssistance`, `receivesSchoolMeals`, requested as `currentBenefits` and worked out in `deriveValues`: a benefit left off an answered list is No). An option is read as the saved codes its words name. A saved code checks the one option that names it; options one code names together (On-Campus Job and Off-Campus Job, both `job`) stay unchecked, and a single-choice question is then left alone. A checkbox question answered only in part is reported in the fill's `partial` ids (a subset of `filled`); while the boxes SecondHand checked are still the only ones checked, each later plan lists it in `matched` with `partial: true`, the worker never fills or holds it again and keeps it in `needYou`, and `navigationFields` reports it unanswered so Fill and continue stops there. Fill sensitive details counts a partial fill as filled and keeps it in `needYou`.

Fill sensitive details (#176): after a fill on an approved site whose `getFields` reply named `held` fields, the worker keeps, per tab and in memory only, the questions of the click's last plan that the rules matched to a key needing one of them (`SecondHandGeneric.requestKeys`, so an age range waits for a held date of birth): `{ frameId, documentId, planId, token, key, label, url, fields }`, with the address of the frame's site and the held fields that question needs. They stay in `needYou`, `result.held` counts them, the summary says how many wait (and a page with nothing else filled says how many need the applicant, not that nothing matched), and they are never `savable`. A reply naming a field the request didn't ask for, one named twice or also answered, an empty or non-list `held`, or any `held` on Iowa's portal is refused as `worker.desktopUnexpected` and fills nothing. They are forgotten when the tab loads a page or closes, the site is turned off or Chrome takes it back, a frame's document moves on (that frame's questions only), or the next Autofill or widget plan replans the page. For the side panel only, `ui:pageState` adds `held: [{ id, label }]` when there are any. `ui:fillHeld { confirmed: true }` is accepted only from the side panel's trusted click. For each site with held questions, in page order, the worker sends `getFields { url, fields, sensitive: true }` with the held fields its questions need; a reply that holds anything back is refused. With the receipt that reply gave, it checks a fresh unlocked status, the tab's address, and fills those questions only, with `secondhand:generic:fill` on the kept plan token (one pass, so the plan and its Save offers stay current). The app answered for that site, so its questions no longer wait, filled or not; one without a saved answer stays under need-you. Cancel ("You cancelled…") is `worker.heldCancelled`: what filled stays, and the site's questions, and any later site's, stay held. The tab's result then counts what filled, drops it from `needYou`, and gives the new `held` count, and the reply is that result. With nothing kept, `ui:fillHeld` is `worker.heldGone`. While its result has `held`, the widget adopts the worker's result at each poll, so its need-you count follows the side panel's fill.

The observed home-only `addressValidation` page can select the first structurally verified suggestion, then continue. Widget/sidebar and desktop trust copy disclose the preference. ## General controls, custom placement, and ordinary continuation

`generic-adapter.js` traverses the current document and open shadow roots only. Labels and ARIA references resolve within the control's own root; radio/checkbox grouping also keeps root identity. It supports native controls, simple editable text boxes, and ARIA radio, checkbox/switch, listbox, or combobox controls with a unique matching saved choice. A combobox needs one root-scoped `aria-controls`/`aria-owns` popup with existing options and explicit selection state. The page must actually open and confirm selection. Existing answers, hidden/disabled/read-only controls, ambiguous references, closed roots, and unsupported widgets are left alone.

`plan()` holds private bindings for element/root/form ownership, labels, types, and option references. `fillFields(document, token, [{ id, custom: true }], { [id]: value })` accepts only the same still-unanswered safe unmatched question, a bounded type-compatible value, and no standard profile-key override. Text is inserted as text, never HTML. An explicit No can complete an unchecked supported checkbox without clicking; an untouched unchecked box is not inferred to mean No. New ARIA/editable support does not enable Laya option guessing in those controls.

`deepQueryAll(document, selector)`, `isRendered(element)`, and `navigationFields(document)` are internal DOM helpers. Navigation fields expose `{ elements, answered, required, safe, supported }` only to the local navigation module. Content endpoints `secondhand:generic:navigation` and `secondhand:generic:advance { token }` carry sanitized navigation metadata and a one-use token; private control/answer snapshots remain in the document. Shadow-root mutations and newly attached open roots update detection. BFCache restoration must recheck current site approval; off scripts never restart themselves.

The explicit **Fill and continue** run is held in worker memory for one active tab and origin, bounded to 64 steps. Each step fills saved rules/custom answers without Laya or Chrome guesses, then requires supported required fields and native validation, no protected step, errors, dialog, unresolved frame, or guessed field, and exactly one ordinary Next control with a same-origin destination. The pre-approval snapshot binds controls, values, hidden payload, form action, button, URL and document; every attempt is recorded before the click, so a lost reply or repeated semantic step is not automatically retried. Missing answers or a guard failure stops the run; the applicant restarts it explicitly after review. Stop, tab switch, origin change, permission/trust revocation, or an invalid/locked receipt also ends it. Ordinary Next can transmit and save draft answers; final actions remain manual.
